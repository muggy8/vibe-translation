# The file map — intake and the four pre-production pipelines

Series intake, the four cumulative reference pipelines, the audit, the handoff, and what each step is declared to leave behind.

Part of the ai-client documentation; the entry point is [AGENTS.md](../AGENTS.md).

## The file map — intake and the four pre-production pipelines
| Path | Role |
|---|---|
| `utils/handoff.js` | Deterministic per-volume translation handoff (no AI): `buildChaptersJson` (chapter list from the bundle segments, carrying `bodyChars`, `empty` and `syntheticTitle` through so a section that converted to nothing — or a section the book never named — is visible in every downstream list), `renderNewEntry`, `buildTranslationBriefMarkdown` (pure — the one-page brief: new terms/voices/style rules from the persisted extraction JSONs, chapter table (a section that is empty in the source and a section the book never titled are both marked in it), pointers to every per-volume + series-level reference artifact), `writeVolumeHandoff` (best-effort writer of `chapters.json` + `translation-brief.md`; called from jump-in-wiki.js on both the processed and skipped paths — a failure warns, never fails a volume). |
| `utils/artifacts.js` | **What each step is supposed to leave behind**, written as data, and the barrel over `utils/artifacts/` (folder table below): per step, the per-volume files it must produce (`volume`), the series-root files it must publish (`series`), the run-folder records a delivery command must write (`run`), and the file patterns whose PRESENCE is a finding (`quarantines` — a `.rejected` file means a gate fired and nobody read it). Every expectation carries a `level`, a `shape`, a one-line `why` and an optional `when` predicate. `test/test-postmortem.js` pins that the step lists cannot drift: `utils/hooks.js` TASKS and `gulpfile.js` PIPELINE_STEPS for the twelve pipeline steps, `package.json` scripts for the four delivery commands. The assessment lives in `utils/postmortem.js`, and the questions about the delivery records agreeing with each other in `utils/delivery-audit.js`. |
| `utils/disputes.js` | The glossary disputes queue — the one channel that carries terminology findings BACKWARDS (deterministic, no AI). The verifier reads the source, and sometimes what it finds is that the GLOSSARY is wrong rather than the translation. `parseGlossaryDisputes` reads the `GLOSSARY DISPUTE:` blocks out of a verifier's reply (term / canonical / proposed / the two quotes); `mergeDisputes` aggregates them by source term across volumes (the same term challenged twice is one dispute with two pieces of evidence, and a report with no evidence never overwrites one that has it); `saveGlossaryDisputes` writes `glossary-disputes.json` + `glossary-disputes.md` at the series root. `verify-translate` records them per chapter and writes the queue; `glossary.js` reads the queue and appends the open disputes to the volume's **extraction** prompt (`buildDisputesNote`), because the read pass is the one place a rendering is chosen now; `loadVolumeReferences` reads it and `chapterTerminology` marks a disputed term in the prompt — still required, but named as provisional, so the QA loop cannot argue with itself. A dispute with no source quote is recorded and flagged `unsupported` (a complaint, not a correction). |
| `glossary.js` | Glossary task logic — **one route, no author agent**: read the volume (one extraction call per chapter-group), file what was found in the volume's reference record, research the terms, **render `glossary.md` out of that record**, run the no-AI cumulative gate, the deterministic audit and one acceptance iteration, then seal. No agent writes the file, and no agent re-types it. The cumulative-document rules (gotcha 64) still apply, in a new shape: the carry forward is the **record's** — `renderGlossary` prints every earlier volume's sealed rows, so nothing copies a document in and nothing rewrites one (`seedGlossaryFromPrevious`, `glossaryWriteInstruction`, `glossaryRecoveryPrompt` and the amend/validator/feedback turns went with the author route, git history at commit `294351c`). The no-AI gate is unchanged: `compareGlossaryCarryForward` / `assertGlossaryCarryForward` / `guardCarryForwardAgainst` / `quarantineDamagedGlossary` / `reportCarryForwardLoss` (the no-AI gate that fails a volume whose glossary lost carried-forward terms, and moves the damaged file to `glossary.md.rejected` so the next volume cannot read it; it reports three legitimate forms of carrying an entry forward — unchanged, `restructured` (widened or split), and `renamed`, see gotcha 68), `glossaryTermSpans` (the alias spellings inside ONE row's term column — the gate compares entries at THAT resolution, because widening a row with a new alias is an improvement and not a loss; see gotcha 65), `glossaryRowText` + `normalizeGlossaryRendering` (the row-wide and rendering-side evidence the rename test uses), and `parseGlossaryTableTerms` (now also returns each row's existing `rendering` and its `notes`, which is what the index, a conflict check and the rename test need). Also the far end of the disputes channel, in a new shape: it reads the series `glossary-disputes.json` and appends the open disputes to the **extraction** prompt (`buildDisputesNote` → `ctx.disputesText`, `glossary/task.js`), because the read pass is the one place a rendering is chosen now; the amend turn that used to settle them and the validator that checked each listed dispute was decided are gone (glossary route slice 2). **After glossary route slice 5 the stage opens no agent turn at all**: the read pass, the research reading call and the grade are three tool-less one-shots, research is bounded to the rows `glossary/researchable.js` says are worth a lookup (`RESEARCH_MAX_TERMS_PER_VOLUME = 12`, a constant with no knob), and what research returns is filed on the volume's record as its own row (`research_notes`) that the render merges into the row's Notes cell — a published row is still never edited. |
| `character-voice.js` | Character voice reference task logic — **one route, no selector**: read the volume chapter by chapter, file what was found in the volume's reference record, and **render** the cumulative `character-voice.md` and the cumulative `pov-map.md` out of that record. No author agent, no feedback pass, one acceptance grade per volume. The cumulative-document rules glossary.js established (gotcha 64) still apply, but they are enforced by code now rather than by instructions to an agent: `parseVoiceSections` + `voicePrimaryName` (the `### Character` sections, each keyed on the part of its heading that says WHO it is about, so a reworded persona tag is not read as a deleted character), `compareVoiceCarryForward` / `assertVoiceCarryForward` (the no-AI gate on the character-section set, which knows the record's roster folds), `parseVoiceQuirks` + `truncateVoiceRef` (the extraction answer's parser and the window shown to the extractor), `buildAlreadyExtractedNote` (the only prompt block the stage builds in code), `runQaLoop` / `acceptanceCheck` (the gate), `characterVoice` (the task) and `assertNoRouteSelector` (the refusal). The seed that copied the previous volume's file in, the inlined section index, the write instruction, the recovery prompt and the scaled author cap went with the route that needed them (git history at commit `75e59a7`). |
| `style-guide.js` | Style guide task logic — extracts style-relevant constructs (honorifics, pronouns, particles, internal-monologue markers, onomatopoeia, POV/scene markers, tense, punctuation, wordplay) and produces a cumulative style guide of rendering policies for the target language. Same cumulative-document rules: `seedStyleGuideFromPrevious`, `parseStyleSections` / `countStyleRules` / `buildStyleIndex` / `styleIndexBlock`, `styleWriteInstruction` / `styleRecoveryPrompt`, `compareStyleCarryForward` / `assertStyleCarryForward` / `guardStyleCarryForwardAgainst`, `styleAuthorMaxSteps`. Its carry-forward gate is deliberately narrower than the other two: it checks the `##` category set the prompt specifies (a guide missing "Address & Honorifics" has lost everything inside it) and REPORTS a drop in the rule count instead of failing on it — a guide that says the same thing in fewer words is not damaged, and a guard that compares free prose starts calling improvements losses (gotcha 65). |
| `jump-in-wiki.js` | Wiki task logic **plus the shared helpers**. The wiki builds cumulatively on the previous volume's `wiki.md` + `shared-wiki.md` (looked up in the manifest's reading order, never by `N-1` folder arithmetic) — a missing/stub previous wiki is governed by `ON_MISSING_PREVIOUS` like the other three cumulative tasks (abort, or warn-and-skip with `skip`). After all volumes: the last existing `shared-wiki.md` is copied to the series artifacts directory (`SERIES_ARTIFACTS_DIR`, default `<SERIES_LOCATION>/shared-wiki.md`); writes the per-volume translation handoff (`utils/handoff.js`) on both paths. |
| `consistency-audit.js` | Final cross-artifact consistency audit (the pre-translation sign-off). An audit agent (gated fs tools, cwd = series root, **writes confined to `consistency-report.md` alone** — the four artifacts are genuinely read-only: a wider gate would let the agent "fix" an artifact by overwriting the very thing it is judging) reads the four series-root artifacts (`glossary.md`, `character-voice.md`, `style-guide.md`, `shared-wiki.md`) and writes `consistency-report.md` (PASS/FAIL verdict + severity-banded findings with quoted snippets). The four artifacts are hashed before the agent runs and re-hashed after; if any changed in flight the audit is void (a structural error — the report signs off a state that no longer exists on disk). No QA loop. Idempotent: content-based — the report also writes a `consistency-report.md.provenance.json` sidecar carrying the sha256 fingerprint of each of the four audited artifacts; the report is skipped while all four fingerprints still match the current files (regenerating any artifact invalidates it). A missing or corrupt sidecar falls back to the legacy mtime check (report newer than all four artifacts). `--force` re-audits. A FAIL verdict is logged loudly but does not fail the task — the report is the deliverable. The `verify-translate` borderline tiebreak (the `AUDIT_*` endpoint re-scoring chapters near the passing line) keeps the auditor's findings when the auditor is the pessimist, so a retranslate of a tiebreak-flipped chapter fixes what the auditor flagged. The task entry is the order of its six steps: `requireAuditArtifacts` → `auditIsFresh` → `auditorApprove` (the single-file write gate) → `runAuditAgent` → `assertAuditedStateUnchanged` (the audit is void if an artifact moved while the agent was running) → `logAuditVerdict`. |
| `get-translation-target.js` | **Series intake (step 0)** — an agent-driven discovery that replaces the old folder-name guessing. `getTranslationTarget()` reuses a valid schema-2 manifest (or runs the intake agent), which explores `SERIES_LOCATION` with the epub tools, decides which files are volumes / the reading order / the series name / the source language, stages each volume's source into the folder it named (**a relative shortcut to the original, not a second copy — gotcha 77**), and writes `<SERIES_LOCATION>/translation-target.json` (schema 2: `seriesName`, `seriesNameAlt`, `sourceLanguage`, `targetLanguage`, `discovery.{summary,confidence,evidence,excluded}`, `volumes[]`) plus the human-readable `translation-plan.md`. Guards: `validateManifest` (schema, folder-name sanitizing, installment numbers, relative source paths, and **each volume's source must live inside its own folder**), `readUsableManifest` (a cached manifest that fails validation is never reused), `readCommittedLayout` + `applyCommittedLayout` (a re-run never renames a folder that already holds pipeline output), `manifestSourcesExist`, `findDuplicateSources` (the same book listed twice is rejected), `validateVolumeIntegrity` (every volume's `integrity` block — the agent's "is this a real narrative?" judgment — must exist and be stated, fail-closed), `checkVolumeSourceShape` + `volumeIntegrityProblems` (the objective "is this a book?" cross-check: no readable text, under the `DISCOVER_MIN_VOLUME_TEXT_CHARS` floor, a binary file renamed, or an archive whose image payload dwarfs a thin prose count), `confidenceGate` (`DISCOVER_MIN_CONFIDENCE`, fail-closed when the agent reports no confidence), `createIntakeApprove` (the plain file tools are shut at `.epub` paths). `discoverSeries()` is the `discover` gulp task. `buildDeterministicManifest` is the no-AI `--dry-run` backend, used only when there is no committed plan (existing volume folders holding a book, or a flat pile of source files staged into folders; `deriveSeriesName` names the series from the books when `.env` does not). An intake that fails every attempt is a **structural** failure: no plan of record means no step can run, so `ON_TASK_ERROR=continue` does not walk past it. All ten tasks read this manifest. |
| `translation-target.json` | Generated manifest (see `get-translation-target.js`); lists each volume's folder, source file, installment number, and metadata. All ten tasks read it to resolve folders and source files. The live series dir always comes from `SERIES_LOCATION` (env), not from the manifest's `seriesLocation` field (provenance metadata — see gotcha 11). |
| `hooks/` | Per-machine hook scripts (git-style; gitignored — only `README.md` + `*.sample` are tracked). Executable before/after hooks for each step and the whole run. See docs/architecture.md "Pipeline hooks". |
| `system-prompts/`, `user-prompts/` | Per-stage prompt pairs. Intake: `translation-target` (system + user — the folder-intake brief: what to look at, how to decide, the exact manifest JSON shape to write). Diagnostics: `diagnostics` (system only — the read-only support team's brief: what a ticket is, what it may look at, that it may not change anything, and the exact JSON answer shape; the tool note is appended in code as `DIAGNOSIS_TOOLS_NOTE` because `AGENT_TOOLS_NOTE` promises five tools and demands writing). Dev team: `devteam` (system only — the role that may change the code: what a ticket and a chosen option are, that it works inside a boundary it may not widen, that it has no shell so the machine runs the checks, and the exact proposal JSON shape; the tool note is appended in code as `DEVTEAM_TOOLS_NOTE` for the same reason). Glossary: `glossary-terms`, `glossary-acceptance` — **two pairs, not five**: the amend, validator and feedback pairs went with the author route that sent them (git history at commit `294351c`), because the stage's validator half is now queries against the volume's record and its document is a render, so neither asks the model anything. Character voice: `character-voice-extract`, `character-voice-acceptance`, `character-voice-detective` — **three pairs**: the compile, validator and feedback pairs went with the route that sent them (git history at commit `75e59a7`), because the stage's validator half is now queries against the volume's record and asks the model nothing; the detective pair belongs to `npm run attribute-voice`, which is not a pipeline step. Style guide: `style-guide-extract`, `style-guide` (compile), `style-guide-validator`, `style-guide-acceptance`, `style-guide-feedback`. Wiki: `jump-in-wiki`, `-validator`, `-acceptance`, `-feedback`. Consistency audit: `consistency-audit`. Translation stage: `translate` (user only — the Index-Translate instTrans single-user-message prompt, Chinese scaffolding with the constraint CONTENT in whatever language it was authored in, **no system prompt file**), `verify-translate` (system + user — source-anchored 0–100 scoring rubric), `polish` (system + user — final proofreading pass, **no source text**), `polish-verify` (system + user — source-aware drift check of the polish pass: does the polished text preserve the verified draft's meaning?). |

## The implementation folders

Each of these modules is a thin public face (`x.js`) that re-exports a folder of cohesive
modules (`x/`). Node resolves `x.js` before `x/`, so every `require("./x")`, every test, and
every test that monkey-patches the harness keeps working unchanged — but the logic lives in
the folder, so open the module that owns the behaviour you are changing instead of reading
the whole layer.

### `glossary/` — the implementation of `glossary.js` (68 lines of face)

**One stage, one route, no author agent.** The glossary file is **rendered out of the volume's
reference record**. The author agent that used to type it, the whole-document validator agent that used
to audit it, the feedback pass that used to rewrite it, and the per-chapter versions of all three were
removed rather than deprecated (glossary route slice 2, 2026-10-13). What the stage still pays for is
one read pass per volume (or per chapter) and the acceptance grades; the file, the validation report and
the cumulative guarantee are all deterministic. The removed prompt pairs are
`system-prompts/glossary.md`, `glossary-validator.md`, `glossary-feedback.md` and their `user-prompts/`
counterparts, and they are gone from the tree, not parked behind a flag.

| --- | --- | --- |
| `glossary/config.js` | 72 | The task's settings and prompt-file paths, read once at module load — **two prompt pairs now**: `glossary-terms` (the read pass) and `glossary-acceptance` (the rubric). The iteration setting the multi-pass stages read is **not** here: one grade per volume is a constant in `glossary/qa.js`, because a number a run can raise is a number a run will raise to make a bad grade go away (AGENTS.md rule 3). |
