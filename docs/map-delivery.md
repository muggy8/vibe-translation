# The file map — running, assessing, and recovering a run

The step runner, the post-mortem, the ledger, the tickets, the two support teams, the patch channel, the manager and the loop that drives it.

Part of the ai-client documentation; the entry point is [AGENTS.md](../AGENTS.md).

## The file map — running, assessing, and recovering a run
| Path | Role |
|---|---|
| `utils/context.js` | **The delivery layer's working memory** — the module that lets a diagnostics or dev-team turn be uncapped without losing what it read (see docs/delivery-layer.md "Uncapped turns" and gotcha 78). Two ideas, both from the ACM paper (arXiv:2607.23809): **offload** (`offload()` — move the bulky results of earlier lookups to a folder on disk, leaving a map in the conversation so the agent knows what it saw and where the text went) and **recall** (`recall()` — plain case-insensitive text search over what THIS turn moved, returning the text verbatim). `CONTEXT_MANAGED_ROLES = ["diagnostics","devteam"]` is the opt-in list and `contextManagementEnabled(name)` is the check — **pipeline stage agents are deliberately NOT in it**, because keeping everything in context is their job. `windowPressure()` + `pressureLine()` measure the conversation against `AI_CONTEXT_WINDOW` and stamp a line onto EVERY tool result ("working window: 11,401 / 16,000 tokens (71%) — getting full. Offload what you no longer need with `manage_context(...)` BEFORE your next read."); ACM measured a model calling tools like these about zero times unaided, so **that line is the load-bearing piece**, not the tools. `createContextTools({state, requestOffload})` builds the two tools the harness adds automatically for a managed handle. `repeatDetector()` is the wall that replaces the step cap (identical tool + identical arguments + identical answer, `AGENT_REPEAT_LIMIT` times), `exhaustionDetector()` catches a trim that keeps trimming with no new work, and `turnClock(maxMs)` is the loose time ceiling. Never moved: a mutating tool's result, an error or refusal, the most recent `CONTEXT_KEEP_RECENT_TOKENS`, user and assistant messages — only old READ answers move, and the call itself stays so `crossCheckReads` can still prove the turn read what it claims. |
| `utils/postmortem.js` | **The deterministic “did this step finish?” check** — no model call, no network, no judgement about quality, and the barrel over `utils/postmortem/` (folder table below). `runPostMortem({ step, seriesDir, manifest, volumeArg, claims })` asks the question `utils/artifacts.js` declares against the disk and returns a `PostMortemReport` of findings (`HIGH` = the step did not finish what it claims to have; `MEDIUM` = a gap worth reading; `LOW` = worth knowing). `--volume` runs skip the series-root expectations (the tasks deliberately do not publish a stale series copy for one volume). A step that declares no corpus output — every delivery command — is not assessed against a plan of record it never read, so `diagnose` and `fix` can be audited without a series folder. `claims` is the delivery half: what the command reports it wrote, which is what its `required` run-folder expectations are gated on. **An assessment that could not run returns `error` + `ok: false`** — never a clean report. `writePostMortemReport` writes `<step>.md` + `<step>.json` to `postMortemDir()`. It deliberately does NOT judge whether an artifact is GOOD — that is the scored gates' job, and a second weaker grader next to the real one is a liability. See docs/delivery-layer.md. |
| `utils/delivery-audit.js` | **The after-run check for the delivery layer itself** — the question every pipeline step gets asked, asked of `delivery.js`, `diagnose.js`, `fix.js` and `autopilot.js`, which had never been asked of them. Three tiers. (1) The records each command claims it wrote are in the run folder and have the shape their renderer always gives them — declared in `utils/artifacts/delivery.js`, assessed by `utils/postmortem/scope.js`. (2) The records agree with each other: a channel that does not parse is `record-unreadable` HIGH (the ledger is the anti-spin gate, and a ledger that cannot be read is a gate that lets everything); a patch answering a ticket that is not in the ticket file is `record-orphan`; a ticket marked `answered` with no diagnosis, or with no options and no `noUsableOptions` saying so, is named; a ticket `closed` with no measured outcome is HIGH, because the ledger will count it as a tried move; a duplicate id is named, because every lookup takes the first; a plan naming a step nothing declares, or claiming an act pass with no execution list, is named; a run lock left by a process that has exited is `run-lock-stale` HIGH — a run that died mid-way, which is the delivery layer failing and nothing noticing — while a lock held by a LIVE run is not a finding at all. (3) **An exit code is a claim**: `claimsFromInvocation` reads the claims off the command line and the exit code rather than taking them from the command being audited, and `claimFindings` checks each against the record — `diagnose` exiting 0 with no diagnosis on the ticket, `fix --commit` leaving a patch `proposed`, `delivery --accept-patch` leaving it unjudged, `--choose` recording a different option. It writes its report beside the other post-mortems, appends an `assessment` entry to the ledger (which is how a delivery finding reaches the next run's triage; `attemptCount` and `isSpinning` select only on `intervention`, so an audit never spends an attempt), never throws, and **never changes the command's exit code** — an audit that can break a finished run is an audit the operator switches off. `auditDeliveryRun({ extraFindings })` is the door the CALLER contributes findings through, which is where a refused manager decision becomes a record: `autopilot/cli.js`'s `refusalFindings()` writes `manager-refused` HIGH when the loop stopped because the manager's own answer was refused, `manager-corrected` LOW when it was repaired and re-asked, and `loop-crashed` when the loop threw — findings the run would otherwise only have printed. It is a leaf module: `utils/tickets`, `utils/patches`, `utils/ledger` and `utils/runlock` each resolve their folder through `utils/postmortem`, so nothing inside that layer may reach back for them. See docs/delivery-layer.md. |
| `utils/ledger.js` | **What a run has already tried, and whether it helped** — the run’s memory, written as data (no model call), and the barrel over `utils/ledger/` (folder table below). Nothing else in the pipeline records a DECISION: `translation-state.json`, the `*-rolling-state.json` files and the verification sidecars all record ARTIFACTS, and none of them can answer “have I already tried this?”. The barrel also holds the three shapes the rest of the layer names in its JSDoc: `LedgerEntry`, `LedgerKey`, `LedgerDecision`. |
| `utils/tickets.js` | **The only channel between the delivery manager and the teams that can see the code.** A ticket is findings-shaped and never outcome-shaped: `createTicket` takes the step, the finding `kind`, the evidence it actually looked at, what was already tried (read out of the ledger by `triedFromLedger`, not from the manager's memory), what was ruled out, and a **question** — and `validateTicketShape` refuses anything else, naming what to write instead: a command (`Disable the guard.`), a demanded result (`Make volume 15 pass`, `so that it passes`, `get rid of the finding`), a request for a banned thing, or a summary with no question in it. `attachOptions` is where the **banned-option filter** runs — on the provider's side of the conversation, because a manager given a menu picks the cheapest item on it, so a rule about the manager's judgment is not a rule. `BANNED_OPTIONS` covers turning off a carry-forward guard, `--allow-fail` / `--allow-no-glossary`, lowering `PASSING_SCORE` or any acceptance threshold, deleting quarantine evidence or reports, editing `hooks/`, declaring an artifact expectation away, flipping an `ON_*` run policy to `skip`, and disabling the ledger — each with the reason and the escalation (**the account owner**). Refused options are **kept on the ticket**, not dropped: a dropped option looks like it was never thought of. `recordChoice` requires a reason; `closeTicket` accepts only `improved` / `unchanged` / `worse` — measured on the deliverable, never `finding-gone`. The other half of the conversation is here too: `recordDiagnosis` is the **only** door from a model reply to a ticket's options (it calls `attachOptions` internally, so the filter cannot be bypassed), `recordAnswer` records the manager's reply to one of the diagnostics team's clarifying questions and refuses to re-answer one that is already closed, `unansweredQuestions` lists what the team is still waiting on, and `customerMayRead` is the table that makes a manager's answer fail when it cites `.logs/**`, a `.js`, a prompt or `hooks/` (the boundary is checked on the ANSWER, not the question). `filterOptions` stamps `outcomeOnlyVerification` on an allowed option whose only stated check is "the finding disappears", so the flag reaches the stored option and `tickets.md` rather than living in the in-memory reply. Written to `postMortemDir()/tickets.json` + `tickets.md`. See docs/delivery-layer.md, gotcha 70 and gotcha 74. |
| `utils/diagnostics.js` | **The read-only support team** — the role that CAN see the code, answering a ticket the delivery manager wrote (one model call per ticket). `readOnlyFsTools({cwd, allowedDirs})` hands the agent **only** `readFile` / `listFiles` / `grep` out of `harness.createGatedFsTools` and returns an `approve` gate that denies every mutating call AND records each refusal — the gotcha-8 two-layer pattern, so a write attempt is reported whichever layer stopped it (`collectWriteAttempts`). `DIAGNOSIS_CONTRACT` is the reply shape it must answer in (`{cause, options:[{label, touches, cost, risk, verify, requiresCodeChange}], recommend, questions, read, ownerNote}`) and `validateDiagnosisShape` is fail-closed on it like `parseAcceptanceReply`: no cause / no options / an option missing label-touches-cost-risk-verify / a bad `cost` word / a question only a code reader can answer are **refused**; a thin cause, no cited reading, a recommendation naming no offered option, an outcome-only `verify`, a cited file the turn never opened, or state that moved during the turn are **warnings**. `crossCheckReads` compares the reply's claimed `read` list against the turn's real tool calls — a `grep`/`listFiles` over a FOLDER covers the files inside it, a call that ERRORED covers nothing, a file the turn got back with `recall_memory` counts as read (it read it earlier and the harness kept the text), and a cited-but-unopened file is reported as `citedWithoutReading`. `diagnoseTicket` fingerprints the ticket's evidence before and after the turn (`stateMovedDuringDiagnosis` — read-only checked against the disk, not asserted), runs the turn **uncapped** (no step cap — see docs/delivery-layer.md "Uncapped turns" and gotcha 78; the role is a managed handle, so its old read answers are set aside on disk instead of compacted away or cut off at a step limit), records the turn's shape with `turnShapeOf`, and reaches the ticket only through `recordDiagnosis`, which runs the banned-option filter internally so no path attaches a diagnosis that skips it. `DIAGNOSIS_TOOLS_NOTE` names the two memory tools the harness adds (`manage_context`, `recall_memory`) even though `readOnlyFsTools` hands the agent only the three read tools — the harness adds the memory pair, so the role's own tool set does not. `ownerNote` is where "I actually believe the guard is wrong" belongs: prose for the **account owner**, never an option. See docs/delivery-layer.md and gotcha 74. |
| `utils/resume.js` | **Where the run stopped, written as data** — the delivery manager's triage (no model call, no code access). `DELIVERY_ACTIONS` is the **closed menu**: every move the manager may propose, as an entry with a `tier` (A = act alone, B = capped, C = never), the primitive it maps to, and `countsAsIntervention` on each one — so "picking up unfinished work is free, destroying finished work is an intervention" is a field the code can act on rather than a sentence in a prompt. Tier C entries carry a `why`, so a refusal can name what it refused, and `actionIsAvailable(name)` refuses anything not on the menu. `readPlanOfRecord` reads `translation-target.json` + `validateManifest` **directly** (never `getTranslationTarget()`, so a triage cannot spend a token or start the intake agent). `inventoryVolume` compares each volume folder against `STEP_ARTIFACT_SPECS` with `{installment}` resolved, and attributes each `.rejected` file to the step whose **artifact it names** (the three cumulative steps share one quarantine pattern, so matching the pattern alone calls a `character-voice.md.rejected` glossary's evidence). `readWorkingState` runs one `runPostMortem` per `PIPELINE_STEPS` entry and splits the HIGH findings into **damage** (work is missing — this decides where to pick up) and **evidence** (a gate refused something — read it, it is not a reason to rebuild); anything HIGH that is not explicitly evidence counts as damage, so a new finding kind cannot become invisible. `planResume` then decides: `resume` / `nothing-to-do` / `evidence` / `blocked`; the wipe list is the resume step's declared outputs only (`.rejected` evidence is never wiped, Tier C); a FAIL audit verdict and a finding the ledger says already survived a run both become **`open-ticket`, not a re-run**; a volume missing a step's output **while holding that step's own quarantine** is the volume-15 shape and becomes a ticket too, because re-running a deterministic gate reproduces the identical quarantine (gotcha 68); later steps report `after` / `blocked` with their own earliest damaged volume; a cumulative cascade is never proposed with `--volume` (gotcha 66). `formatRanges` + `progressByStep` render "glossary is whole through 14, missing 15–17" instead of seventeen folders of file names. `maxInterventionsPerStep` (`DELIVERY_MAX_INTERVENTIONS`, default 5) and `interventionsUsed` read the **per-step** budget out of the ledger's `intervention` entries for the newest recorded run — counting only the menu entries marked `countsAsIntervention` — and `planResume` turns a step that has spent it into `open-ticket`. `unhelpfulInterventions(entries, run)` is the second question the ledger answers — the interventions on each step that ended `unchanged` or `worse` — because the disk cannot tell a repair that failed from work that was never done: a step killed part-way through leaves the same folder either way, and the only reading of it that does not invite a second identical attempt is the record that an attempt already cost a step run and moved nothing (gotcha 89). Every plan line carries the `finding` kind the action is a response to, because the anti-spin gate keys on it; a step that is complete and is only in the plan because the resume step's fix invalidates it **inherits the finding the whole plan is a response to**, since otherwise the memory has nothing to key on and "have I already run this step in this sequence, and did it help?" becomes unanswerable. `readWorkingState` also keeps the HIGH findings themselves on the step state (`damageFindings` / `evidenceFindings`, each with `kind` / `file` / `volume` / `message`) — a ticket must cite what the manager looked at, and this assessment is the only thing it is allowed to have looked at. `readDeliverable` reads the publish report through `utils/translation-report.js`'s own reader and roll-up, so the triage and the before/after comparison cannot count one report two ways. `progressForStep(volumes, step)` is still exported for reporting a step's progress; act mode's verdict comes from `utils/delivery-verify.js`. **The triage reads its own correspondence**: `readWorkingState` attaches `tickets` / `ticketsError` / `patches` / `patchesError` so `planResume` stays a pure function of a state snapshot (a hand-built test state must not silently read the live series' history — gotcha 71), and `planResume` computes the repair shape FIRST and then runs the four "re-running reproduces the same result" checks through one `escalate(kind, subject, reasons)` helper that either overwrites the plan with `open-ticket` or is **superseded**: an existing non-closed ticket for that exact `(step, volume, finding)` is named on the plan line (`plan.existingTicket`) instead of a duplicate being proposed; an `accepted` or `committed` patch answering it turns the escalation back into `run` / `wipe-and-cascade` with a reason naming both (an `accepted` one also says the commit is still owed); a ticket closed `unchanged` / `worse` keeps the escalation and says time passing does not make a re-run legitimate; and a `proposed` patch answers nothing, because unjudged code in the tree is what gates act mode. The supersede is deliberately **not** applied to `intervention-budget` — a code change cannot un-spend attempts this run already made, and applying the patch is itself the counted wipe-and-cascade — so that escalation stands and names the account owner as the one who raises `DELIVERY_MAX_INTERVENTIONS`. `ESCALATION_HEADLINES` keys the headline on `plan.action`, so a superseded gate-removed escalation reads as a run. See docs/delivery-layer.md and gotcha 71. |
| `utils/delivery-verify.js` | **Did the intervention help the book?** — the acceptance test for an intervention (deterministic, no model call). The barrel over `utils/delivery-verify/` (folder table below), and the home of the two shapes every consumer names in its JSDoc: `DeliverableSnapshot` (one measurement) and `SignalMovement` (one signal’s movement between two measurements). `measureDeliverable` takes the measurement, `compareDeliverable` answers `improved` / `unchanged` / `worse`, and act mode’s ledger entry and a ticket’s closure both come from that one comparison. See docs/delivery-layer.md and gotcha 73. |
| `delivery.js` | **The delivery manager's CLI** over `utils/resume.js` — thin on purpose: it reads a state, prints the plan, writes it, and in `act` mode executes it. `--mode=report` (default, from `DELIVERY_MODE`) or `--mode=act`; `--series=<dir>`; `--json`; `--no-write`; an unknown flag is refused with exit 2, because a mistyped flag on a tool that reads a live series should fail. Every action the plan names is re-checked against `DELIVERY_ACTIONS` (exit 2 if it is not available), so a future edit to `planResume` cannot invent a move. **Act mode** gates each step (menu → per-step budget → anti-spin), wipes the step's declared outputs, spawns the real step runner (`node index.js --stages=<step>` with `INDEX_RUN_ID` and `SERIES_LOCATION` set explicitly), re-reads the state, judges the outcome by comparing the deliverable before and after (`utils/delivery-verify.js` — `improved` / `unchanged` / `worse`, with the account of what moved), records the attempt in the ledger under the **newest recorded run** (so the anti-spin gate can see the whole story) together with the before/after signal account, opens a ticket when a gate refuses, and stops the sequence at the first refusal or failed step. `closeTicketOnDeliverable` closes a ticket by re-measuring now and comparing against the snapshot taken before the fix, through the same `closureFromComparison` act mode writes to the ledger — so the manager cannot record `worse` in one place and `improved` in the other. It refuses to run while a pipeline run holds the run lock, refuses `--no-write` together with `--mode=act` (exit 2 — a rehearsal that records is a contradiction), and executes nothing when the plan's own answer for the resume point is a ticket. **The three verbs on the escalation ladder** are the commands behind menu entries that had none: `--open-ticket` writes the question the triage's own escalation names (`questionForEscalation` is keyed on `plan.escalation`, so a gate-removed finding gets a question about the gate rather than the "already tried and it did not move" wording, which would state an attempt that never happened), and it is **idempotent** — a live ticket for that exact step/volume/finding is named, not duplicated, so `autopilot.js` may call it every iteration; `--choose=<optionId> --ticket=<id> --reason=<text>` records the manager's pick (`decidedBy: "delivery-manager"`) and prints `npm run fix -- --ticket=<id>` when the option needs code, which is the door the dev team is summoned through; `--accept-patch` / `--reject-patch` judge a proposal. Each is one act at a time (two in one command is refused, exit 2), `--open-ticket` and `--choose` are allowed in both modes because a ticket and a choice are the manager's own words rather than an action on the corpus, and both are refused with `--no-write`. Exit 0 completed, 1 stopped short, 2 refused the request itself. Writes `postMortemDir()/delivery-plan.md` + `.json` (the manager's own report lives beside the step reports). No `AI_*` variable is read, and no model call is reachable from it. |
| `utils/patches.js` | **The patch channel** — the only place a code change becomes a record, and the rules that say what a change may touch (no model call). `BANNED_PATCH_PATHS` is the table: the guard tables themselves (`utils/{tickets,resume,delivery-verify,ledger,runlock,patches}.js`), the tests that pin them, `hooks/**`, `.env` / `.env.example`, the machine state (`.postmortem/`, `.logs/`, `.dry-run/`), the corpus (generated artifacts, `test-series/`, `.rejected` evidence, `-rolling-state.json`), and anything outside `ai-client/`. Each rule has an `id` and is evaluated **specific-first, catch-all-last**, so a refusal names WHICH rule it hit; a path that cannot be normalised to project-relative is banned, not allowed (`path-outside-project`). `normalizeProjectPath` resolves an absolute path against the root it was given (the ticket brief names the root in full, so an agent using the path it was handed must not be refused for it). `isProjectSourcePath` is a **whitelist** (`test/`, `utils/`, `configs/`, `system-prompts/`, `user-prompts/`, root-level `*.js`/`*.md`/`*.json`) because `ai-client/` also holds the run's own output — "allowed unless listed" would default to editing the evidence. `REQUIRED_CHECKS` pins `npm test` then `npm run pipeline-loop`; `runChecks` runs them through the shell (`npm` is a `.cmd` shim on Windows) with a 30-minute ceiling and stores `{id, command, exitCode, passed, tail, at}`; `normalizeChecks` takes the command from the table, never from the caller, so an unpinned id is reported MISSING rather than trusted. `readTestChain` + `testChainIsIntact` refuse a patch that removes a suite from `scripts.test` (the banned-path table cannot catch that: `package.json` is not a banned file). `PROPOSAL_CONTRACT` + `validateProposalShape` are fail-closed on the proposal: missing field / unusable path / banned path / a signal the acceptance test does not measure / a change the proposal does not name are **problems**; a thin summary, an outcome-only `verify`, a declared-but-unchanged file, a grown test chain, or touching a scripted-model answer key are **warnings**. `recordProposal` is the **only door** from a dev turn to a patch record and it attaches the proposal once; a refused attempt is stored in `refusedAttempts` (history) and does not stay in `problems` (the current state). `recordChecks` re-runs only for `proposed`/`verified`, and a failing re-verify moves a `verified` patch back to `proposed`. `judgeChecks` splits "never ran" from "ran and failed". `acceptPatch` / `rejectPatch` require a reason, and `judgmentReasonIsSound` refuses "volume 15 passes now" — a judgment about a patch is about what it changed, not about the complaint stopping. `pendingPatches` / `unresolvedPatches` are what act mode reads: an **unjudged patch is live code**, so act mode refuses the whole plan while one is open. `commitPatch` stages ONLY the patch's declared files (never `git add -A`), refuses unless the status is `accepted`, and refuses when the tree holds changes the patch does not declare; `revertPatch` restores tracked declared files and NAMES the files the patch created instead of deleting them (deleting is Tier C). `gitRootOf` asks git for the repository root instead of guessing from the folder layout, and `workingTreeChanges` scopes `git status --porcelain -uall` to that root — `-uall` because plain `--porcelain` collapses a brand-new folder into one entry, and both the "extra changes" list and `leftBehind` must name FILES. `renderPatchesMarkdown` / `renderProposalMarkdown` print what the manager can check, including the checks that never ran and the attempts the machine refused before this one. See docs/delivery-layer.md and gotcha 75. |
| `utils/devteam.js` | **The dev team** — the role that may change the code, and the turn that does it (one model call per patch). Barrel over `utils/devteam/` (folder table below): the gate that refuses `deleteFile` outright and refuses every path `patchPathIsBanned` names, recording `{tool, path, rule, reason, at}` — the same two-layer shape as `utils/diagnostics.js`, because a role that can write needs its refusals written down, not just felt. The dev turn runs **uncapped** (no step cap — docs/delivery-layer.md "Uncapped turns", gotcha 78): a dev turn reads code before it writes it, which is exactly the turn a step cap punished, so it is a managed handle instead — its old read answers are set aside on disk when the window fills, and `turnShapeOf` records what the turn actually did. See docs/delivery-layer.md and gotcha 75. |
| `utils/manager.js` | **The delivery manager's own decision, as one agent turn whose tools ARE the menu** — the only part of this layer that needs a model, and the only part where the "never sees the code" guarantee has to be a capability rather than a sentence: the handle is handed one tool set and it is the offered moves, with no file tool, no shell, no wiki and no context tools. `MANAGER_ACTIONS` is the closed vocabulary of *decisions* (`run / diagnose / answer / choose / fix / judge / escalate / end`) — different from `DELIVERY_ACTIONS`, which is the vocabulary of pipeline *primitives* — and `ACTION_MENU_ENTRIES` maps each decision to the menu entry that gives it a command, so a decision the loop cannot carry out is caught by a test instead of discovered by a run. `MANAGER_RULES` is the standing contract (what it may read, what it may never read, what it may never do, its two limits) and it is the turn's **system prompt**, stated once per call so every decision in a run is made under one contract; `MANAGER_TOOLS_NOTE` is the tool-shaped half, appended in code. `renderManagerBrief` builds the state report from records this layer already wrote for a human — the triage, the deliverable counts, the remaining per-step attempts, each ticket via `renderTicketForManager`, each patch via `renderPatchForManager`, and the offered menu both as lines and as tool names — and nothing else: no file is read, and the only place a source path reaches this role at all is a patch's declared file list. `buildMoveTools` is the closed menu made structural: a move the state does not support is a tool that does not exist, and the ids ride inside the tool. `parseManagerAction` is the kept text path, fail-closed (the LAST fenced block wins, for the same reason as the dev team's; a missing `reason` or a missing per-action field is not a decision). `validateManagerAction` is the gate on both paths: `run` must name the step on the offered menu; a ticket must exist; a diagnosis may not be asked twice (`--reask` is the account owner's move); an answer may only cite what `customerMayRead` allows and must say WHICH question it answers; a chosen option must be one the filter allowed and must be the reason the dev team is called; a judgment must be about the change (`judgmentReasonIsSound`) and about a patch that is still unjudged; an escalation must be a sentence, not "idk"; `end` goes through `endIsProvable`. `endIsProvable` and `safeToAcceptAutomatically` are the two claims this module refuses to take on faith — the first against the records, the second against ordinary-code + green-checks + no-regression. `managerDecision` is wrapped in `runTurnWithHooks(MANAGER_TASK, …)` so the role's own model switch fires around its own turn, and it is the reader of `DELIVERY_MAX_TOKENS`. A dead call names the wrong-container suspicion out loud. See docs/delivery-layer.md and gotcha 76. |
| `autopilot.js` | **The loop that drives a run**: read the state → open the ticket the triage says is the answer → offer the menu → ask the manager → type the command for its answer → re-read. Barrel over `autopilot/` (folder table below). It owns no gate, no budget, no wipe, no measurement and no record; every move is the account owner's own command spawned in its own process (`delivery.js --mode=act`, `diagnose.js --ticket=…`, `delivery.js --choose=…`, `fix.js --ticket=…`, `delivery.js --accept-patch=…` then `fix.js --commit=` / `--revert=`), which is both the reload boundary a code fix needs (gotcha 66) and the reason the loop cannot reach past a gate. `offerMoves` puts **exactly one `run` move** on the menu — the plan's entry point, labelled with the steps the same sequence then runs — because offering the later steps separately would let the manager skip the cascade. `commandFor` / `describeCommand` are one function, so watch mode prints the exact command act mode runs and the two cannot drift. `AUTOPILOT_MODE` defaults to **watch**: decide, print the decision + the whole menu + the command, and write nothing at all (no ticket, no ledger entry, no plan file, no lock) — the only safe rehearsal, since act mode refuses `--no-write` (gotcha 72). It takes **no run lock of its own** (its children take their own) but checks `runInProgress()` before each action and refuses to act beside a run. An accept is the one move it will not take on the manager's word: `safeToAcceptAutomatically` decides, and anything else stops and names the account owner. `AUTOPILOT_MAX_ITERATIONS` (default 12) is a wall, not a budget. No `--dry-run` — that flag also suppresses hooks, and the hooks decide which container answers (gotcha 22). See docs/delivery-layer.md and gotcha 76. |
| `diagnose.js` | **The diagnostics team's CLI** over `utils/diagnostics.js` + `utils/tickets.js`: `--ticket=<id>` answers one ticket, `--open` lists the tickets that have no answer yet, `--answer=<text>` (with optional `--question=<text>`) records the manager's reply to one of the team's clarifying questions, `--reask` allows a second diagnosis of a ticket that already has one, `--series=<dir>` (default `SERIES_LOCATION` — and a folder inherited from the pipeline's default source folder is refused, because a diagnosis is an answer about ONE run, gotcha 79), `--json`. An unknown flag is refused with exit 2. Re-asking without `--reask`, a closed or unknown ticket, and answering before a diagnosis exists are all refusals (exit 2) that happen **before any model call is reached**. It warns — deliberately does not refuse — when the run lock is held: reading a moving state is harmless for a role that cannot write, so the diagnosis is labelled a snapshot instead of being blocked. ## The implementation folders

Each of these modules is a thin public face (`x.js`) that re-exports a folder of cohesive
modules (`x/`). Node resolves `x.js` before `x/`, so every `require("./x")`, every test, and
every test that monkey-patches the harness keeps working unchanged — but the logic lives in
the folder, so open the module that owns the behaviour you are changing instead of reading
the whole layer.

### `index/` — the implementation of `index.js` (98 lines of face)
