# Gotchas 64–69 — cumulative documents that outgrow one reply, and the runner that needs a memory

> Gotchas **64–69** of the AGENTS.md gotcha list. The whole list is indexed from AGENTS.md §2.

Hard-won: each one exists because of something that went wrong on a real run.
Part of the ai-client documentation; the entry point is [AGENTS.md](../AGENTS.md).

64. **A cumulative document eventually outgrows one reply, and a prompt that asks a model to reproduce it destroys the part it could not reach.** Every glossary pass used to end with "write the complete glossary to `glossary.md` using `writeFile` (complete contents, overwrite)". That is right for volume 01 and impossible from volume 03 onward: the output cap is a quarter of `AI_CONTEXT_WINDOW` (`envMaxTokens`, so 65,536 here), and the cumulative glossary measured 16 KB at volume 01, 45 KB at volume 02, **230 KB at volume 03, 268 KB at volume 04, 474 KB at volume 05**. Measured on the live 17-volume run: 25 step-cap warnings, all in the glossary stage, all on volume 03 or later (17 amend turns, 7 feedback turns, 1 findings merge); one turn's `writeFile` JSON argument was cut off **mid-string** and the tool call failed outright, killing volume 04 (its folder has a `glossary.md` and nothing else — no validation report, no coverage audit, no rolling state); the capped turns ended `finish_reason=tool-calls` still mid-work after 37–64 tool calls, 8–17 paged `readFile` calls and 16–39 `editFile` patches; `glossary-amend` alone cost 234M of the run's 465M tokens (~7.8M prompt tokens per call, worst single turn 14.1M). The failure class, not the model, is the thing to fix — **raising `maxSteps` only buys more paging and more tokens.** Four rules now stand together:
   - **The workflow copies the baseline in** (`seedGlossaryFromPrevious`) before any agent touches the volume folder. "Carry forward every existing term" was never a job for a model; it is a file copy. A re-run also RESETS a half-written glossary to the previous volume's clean baseline, which is what "carry forward" means.
   - **The instruction follows the file** (`glossaryWriteInstruction(hasExistingFile, mode)`, one implementation for the amend, feedback and per-chapter passes, and the same rule in `glossaryRecoveryPrompt`): an existing file is amended **in place with `editFile`**, and the whole-file `writeFile` is explicitly forbidden. Only the first volume (or a failed seed) is told to write it whole. The recovery turn used to demand the exact instruction that broke the file — it now edits.
   - **The agent gets a map, not a hunt** (`buildGlossaryIndex` → `glossaryIndexBlock`): every section with its terms and existing renderings, inlined, so placement and conflict checks need no paging. Capped by `GLOSSARY_INDEX_MAX_CHARS` (30000) and it **says** when it truncates (gotcha 43).
   - **A deterministic gate checks the invariant** (`compareGlossaryCarryForward` / `assertGlossaryCarryForward`, no model call). Nothing else in the stage can see a lost term — the validator reads this volume's source and the current glossary, and its own prompt tells it "you do not have the earlier volumes' sources". Observed: **volume 06 shipped 411 of volume 05's 769 terms** (59% gone) and volume 03 silently lost 8 while being accepted at 78/100. The gate fails the VOLUME and moves the damaged file to `glossary.md.rejected`, because a failed cumulative volume normally stops the next one only when its artifact is MISSING — a present-but-short one is the case `ON_MISSING_PREVIOUS` cannot see, and it would have been read as terminology law by every later volume. The chunked flow runs the gate **between chapters** (that is where volume 06's terms actually disappeared, and catching it at chapter 3 saves eight chapters of work on a broken base). Knob: `GLOSSARY_CARRY_FORWARD_GUARD=false`.
   The step caps that ran out are now scaled (`authorMaxStepsFor`, `findingsMergeMaxStepsFor` — the findings-merge agent's flat 20 lost a whole validation round on a 10-chapter volume after 34 read/grep calls), and the harness's truncation-guard warning goes through `logLine` so it actually reaches `summary.log` (it used to be a `console.warn`, which is why volume 04's cause was invisible in the log file and visible only in the per-turn chat dump). Related: gotcha 58 (an agent that cannot read what it must preserve starts reconstructing it from memory — this is the same failure at the other end of the size range), gotcha 14 (the 64 KB truncation of the injected reference), gotcha 43 (a silent truncation is a silent omission), gotcha 65 (the same failure in the other two cumulative stages, plus the two things that made it invisible: a guard that called an improvement a loss, and a QA loop that could not tell a rewrite from a no-op).

65. **A step-cap warning is a workflow shape, not a model weakness — and a QA loop that cannot tell a rewrite from a no-op pays for the same document twice.** The character-voice and style-guide stages never got gotcha 64's fix, and the live run showed why they needed it. Volume 01's character-voice feedback turn made **46 tool calls — 29 reads, 15 searches, ZERO writes** — spent 2.63M tokens, and ended `finish_reason=tool-calls` at a flat `maxSteps: 30` while it was still verifying findings, because the one write it had been told to do was the LAST thing in its instructions ("read the source in full", "verify every fix", then "write the complete corrected files"). `character-voice.md` and `pov-map.md` were never touched. Three consequences, and each one needed its own fix:
   - **Nothing detected it.** Both files existed and were real, so `assertWroteWithFallback` reported no gap, no recovery turn ran, `assertRealOutput` passed, and the loop recorded the turn as a normal iteration and started iteration 2 — which paid **8.4M tokens** to re-audit a document that had not moved. Every existing check asks "is the file there?"; none asked "did this pass do anything?". The fix is `fingerprintFiles` (utils/fs.js): the shared loop hashes the artifacts before `runFeedback` and again after it, and byte-identical means the pass produced nothing — log loudly, record `stalled: true`, stop. The four chunked loops run the same check inline.
   - **The prompt demanded the impossible shape.** Both stages' system and user prompts said `writeFile (complete contents, overwrite)` for a cumulative document, which contradicted what the code now instructs and is the instruction that broke the glossary (gotcha 64). The prompt files now name the files and defer HOW they are written to the turn instructions (`voiceWriteInstruction` / `styleWriteInstruction`), which is what `glossary.md`'s prompts already did. The feedback prompts also stopped saying "read the following materials **in full**" and started saying "read selectively, batch your checks (one grep can cover several findings), apply each fix as soon as it is confirmed" — and the turn preamble now orders the work HIGH → MEDIUM → LOW, so a turn that runs out of steps still left a better document behind. The step caps are scaled (`voiceAuthorMaxSteps`, `styleAuthorMaxSteps`, and `findingsMergeMaxStepsFor` in both chunked loops) instead of a flat 30 / 20. The seed + index + edit-in-place rules themselves are the same four rules gotcha 64 lists, now in all three cumulative stages.
   - **The acceptance loop was buying its own second sample at the most expensive price available.** `ACCEPTANCE_MIN_SAMPLES` is `min(2, ACCEPTANCE_WINDOW_SIZE)`, so volume 01's voice reference scored **76/100 against a passing score of 69 — a passing grade — and still could not accept**, because the window needed two samples and had one. The only route to the second sample was a feedback rewrite plus a full re-audit: 2.63M + 8.4M tokens for evidence a 55k-token grade produces. `confirmPassingScore` (`ACCEPTANCE_CONFIRM_ON_PASSING`, default ON) takes the missing samples from the same artifact — one at the judging temperature, the last at temperature 0 — and puts them INTO the window. It is not a lower copy of the exceptional path: that one keeps its confirmations out of the window on purpose, because a failed consensus must lead to the ordinary loop and not to an acceptance built from the grades that just failed. This one is filling the window, so a re-grade that FAILS is the correct outcome — it is the signal that the feedback round the loop was about to run is genuinely wanted.
   **The guard itself had a false positive, and it was destroying good work.** `compareGlossaryCarryForward` compared term cells as exact strings, so an agent that WIDENED a row with a new alias looked like one that deleted it. Volume 02 was quarantined for "dropping" two terms that were both still in the file: `三つ編み魔王 / 三つ編み悪魔 / 呪われし姫君` had become `三つ編み魔王 / 三つ編み悪魔 / 魔王 / 呪われし姫君`, and `鈍感系巻き込まれ型主人公` had gained two aliases — a glossary that had grown 88 terms → 140, thrown away. The gate now compares entries at SPELLING resolution (`glossaryTermSpans`): an entry is carried when every spelling its term column named is still present somewhere (its own row, a longer row, or split across several), and `restructured` counts those so a reword is visible instead of being counted as a loss. The same lesson shaped the other two gates: the character-voice gate keys on `voicePrimaryName` (the persona tag `【俺人格】` is the half a feedback pass is most likely to reword, and a heading COUNT dropping is what proves a real deletion), and the style-guide gate checks only the `## ` category set the prompt specifies and REPORTS a drop in the rule count rather than failing on it. The rule to keep: **a carry-forward gate protects the terminology, not the formatting of the rows that held it** — a guard that calls an improvement a loss quietly destroys the work the pipeline paid for, and it does so while looking like it is enforcing rigor.

66. **A running Node process cannot pick up a code change, so the reload boundary is the process — and the pipeline already had one.** The self-repair idea this project is moving toward needs a way for a fixed module to become the code the rest of the run executes. In-process hot-swapping does not work here, for three reasons that are all specific to this codebase: `gulpfile.js` requires all ten task modules at the top of the file, so Node's module cache holds them for the whole run; every task module captures its settings at load time (`const seriesDir = process.env.SERIES_LOCATION` in glossary.js:76, `const tiebreakBand = …` in verify-translate.js:155), which is why every test spawns a child per task; and evicting one module from the cache leaves the new module beside every old reference already captured — gulpfile's destructured `const { glossary }`, the re-export chains between `translate.js` / `verify-translate.js` / `utils/translate.js`, and any agent session mid-turn — which produces a volume half-built by old code and half by new. That is not a fix; it is a new bug class of exactly the kind this list is full of. The fix is `index.js`: **one step per process**, which is cheap here for a reason worth remembering — the idempotent skip-checks make a re-run nearly free, and a process start is NOT a model container switch (`hooks/.model-switch-state` makes a repeat switch a no-op, gotcha 22), so the expensive thing in this pipeline is a container switch, not a process. Two consequences to keep: **(a) a patch may not land mid-step.** The cumulative tasks' carry-forward gates compare a volume's artifact against the previous volume's; if the code changed between them, a "loss" may be the code change rather than a data loss, and the gate would quarantine good work (gotcha 65). Fix loops belong at step boundaries. **(b) the skip checks do not know the code changed.** They key on source fingerprints, rolling state and `contextHash` — none of which include a code version — so after a patch a plain re-run skips everything and the fix never executes. The primitive that makes a patch take effect is deleting the affected volume's outputs AND its `*-rolling-state.json` (`wipeAttemptOutputs` already does exactly that, deliberately), which is also what sets `regeneratedAny` and rebuilds the tail. `--force --volume NN` does NOT cascade (the volume filter puts one volume in the loop, so later volumes stay built on the old one) — quarantine-and-cascade is the correct primitive, not force. See docs/delivery-layer.md.
67. **The expensive failures in this pipeline are not crashes, and a runner that reacts only to exceptions would have caught none of them.** Every failure this list describes was found by a human reading `.logs/` the next morning: 457 glossary terms vanished with no error (gotcha 64); volume 06 shipped 411 of volume 05's 769 terms and was **accepted at 78/100**; volume 04 has a `glossary.md` and nothing else — no validation report, no coverage audit, no rolling state; a 164-character sentence about an agent's plan became the series' published character voice reference and passed `assertRealOutput`, the acceptance loop, the validation report and the last-good-volume copy walk (gotcha 58); 554 spine pages became 35 fake chapters and the pipeline translated the copyright page (gotcha 52); `TRANSLATE_CHUNK_CHARS` split 55 of 133 chapters for no reason (gotcha 57); a feedback pass made 46 tool calls, wrote nothing, and the loop paid 8.4M tokens to re-audit an unchanged document (gotcha 65). **Not one threw.** So the check that would have caught most of them is not an error handler — it is an invariant question the code never asked: *did this step leave the files this step always leaves, in the shape those files always have?* That is `utils/artifacts.js` (the declaration) + `utils/postmortem.js` (the deterministic ask), run per step by `index.js` before the next step starts. Two rules to keep. **The assessment must be deterministic-first**: 17 volumes × 9 steps is 153 assessments per run, and a model call reading log transcripts to audit things that are fine turns the auditor into the most expensive stage in the pipeline (the live run measured 465M tokens). Tier 1 costs nothing; only what it flags is worth a model call. **And the check must not over-declare.** `required` is reserved for files the pipeline writes on every path it can reach, and the known-file vocabulary must be complete — otherwise every staged book, every extracted chapter and every piece of deliberately-kept evidence becomes a finding, and a checker that fires on healthy output is a checker people learn to ignore. **And a `catch` that says nothing is where this class hides.** `character-voice/chunked.js` and `style-guide/chunked.js` each called their task's extraction parser without importing it. The call sits inside a `try` whose bare `catch {}` swallows whatever arrives, so the missing name became a `ReferenceError` that was thrown, caught, discarded, and reported as "unparseable chapter output" — and the volume's *what's new in this volume* file (`character-voice-new.json`, `style-guide-new.json`) was written as an empty array on every chapter-by-chapter run. The file existed, was valid JSON, and was the right shape; the artifact assessment had nothing to complain about, and the translation handoff reads that file without a model call. Found only by scanning each file for names it uses but never imports. `test/test-chunked-preproduction.js` now pins it: the extraction stub answers with one parseable entry per chapter and the test asserts the persisted file holds one entry per chapter, so the swallowed name fails loudly. The general rule: a bare `catch` is allowed only where the fallback is *named* and the failure is *counted* — otherwise it converts a crash into a quietly wrong artifact, which is the failure this whole gotcha is about. That is gotcha 65's lesson in its general form, and it is why `test/test-postmortem.js` asserts BOTH halves: a clean series reports nothing, and ten planted defects are all detected. See docs/delivery-layer.md.

68. **A carry-forward gate that cannot tell a rename from a deletion will destroy the edit its own prompt asked for.** The gate fixed by gotcha 65 still read only the glossary table's **first column**. Volume 15 of the live series died there. The chain, end to end: (1) the term-extraction pass sees a *truncated* copy of the previous glossary (445 rows, 200 shown), and the relevance rule keeps a row when its term cell occurs verbatim in the text being processed (`src.includes(cells[0])` in `truncateGlossary`) — the chapter prints `双ふた花ばの恋こい物もの語がたり`, the glossary holds `双ふた花ばの恋物語`, different strings, so the row was not in the excerpt; (2) the extractor re-proposed it as a new term, despite the truncation note telling it not to (a warning about content the model cannot see is not a rule); (3) the amend agent reconciled the two spellings into one row **exactly as `system-prompts/glossary.md` instructs** — "If a new term conflicts with an existing one (e.g., the same character appears under two spellings…), reconcile them to a single canonical form and note the change" — moving the old spelling into the Notes column as "also written …"; (4) the gate searched only term cells, found the old spelling nowhere, called it a dropped term, quarantined the glossary, and with `ON_VOLUME_ERROR=abort` + `ON_TASK_ERROR=abort` stopped a 12-hour, 249M-token run and left volumes 15–17 unbuilt. **The glossary had grown from 445 terms to 460.** The gate's own message blamed the wrong thing ("A pass that rewrites the whole file cannot finish it: the cumulative glossary is larger than one reply can write"), which is why an automated fixer chasing the exception found nothing — nothing was broken except a contradiction between the prompt and the guard. Four rules now stand:
   - **The gate knows the third legitimate form.** An entry is carried when its spellings survive in the term columns (unchanged, widened, split — gotcha 65) **or** it was renamed: a row this volume produced records every old spelling somewhere in the row (`glossaryRowText` — term, rendering, Notes), or the row carries the same target-language rendering and that rendering is unique on both sides (`normalizeGlossaryRendering`). `compareGlossaryCarryForward` returns `renamed` separately, `logRenamedTerms` prints each one (`old → new [section]`), and a renamed row is not counted in `added`.
   - **The rename test only trusts a row that is this volume's new work.** A row already carrying a carried-forward term is not the row the missing entry "moved into", so an incidental mention in someone else's Notes cannot hide a real deletion. And a spelling shorter than `CARRY_FORWARD_MIN_ALIAS_SPAN_CHARS` (2) proves nothing by substring matching — a one-character term occurs in half the Notes cells of a real glossary.
   - **The validator is told renames are expected output.** `system-prompts/glossary-validator.md` has a "Renames are expected output" section and a `Renamed Entries` report section: a rename is not a dropped term, the fix is never "add the old spelling back as a second row" (that manufactures the duplicate the one-canonical-rendering rule exists to prevent, and the consistency check would then flag it), and the one thing the validator *can* check — because it has this volume's source — is whether the new spelling is a form the source actually prints. `glossary-feedback.md` carries the matching rule so a feedback pass does not undo the rename.
   - **The failure message now reads the evidence.** It says whether the file shrank (the shape of a reply-budget cut-off) or did not (the shape of a replaced row), instead of asserting the first.
   The same incident has two follow-ups that are NOT fixed here and are worth knowing: `truncateGlossary`'s relevance test compares the **whole term cell** against the text, so an alias row (`A / B / C`) can never match and is systematically dropped from the window (20 of 445 rows on the live series); and the extraction prompt's "do not re-add a term as new merely because it is absent from what you can see here" is unenforceable while the list it refers to is truncated. The honest fixes are span-level relevance matching and handing the extractor the complete term list (445 terms ≈ 6 KB). `test/test-glossary-load.js` pins all four rules above, in both directions: the volume-15 rename passes, a deleted entry with no trace still fails, and an incidental mention still fails.

69. **A runner with the authority to re-run steps needs a memory of what it already tried, and a test that exercises that runner must not be able to touch the work it delivers.** Two halves, learned in the same sitting.

    **The spinning half.** The delivery-manager design hands an agent authority to re-run a step, wipe a volume's outputs and cascade, force a re-audit. Its predictable failure is not danger — it is **spinning**: a finding appears, the step is re-run, the identical finding appears again, it is re-run again, and a 12-hour run ends where it started. Volume 15 (gotcha 68) is exactly this shape: re-running a deterministic gate produces the identical quarantine every time, because the finding was never about the data. Nothing in the pipeline could see this, because everything that persists — `translation-state.json`, the `*-rolling-state.json` files, the verification sidecars, the provenance sidecars — records **artifacts**, and none of them records a **decision**. So `utils/ledger.js` is the run's memory, and the rule it enforces is `TRANSLATE_QA_RETRY_BUDGET` lifted to run level: the same action against the same finding, ending `unchanged` or `worse` twice in one run, is refused, and the refusal names the next step (open a ticket) rather than just saying no. Three properties keep it from becoming the guard that gets switched off (gotcha 65's lesson again): only *repetition* is blocked — a different action or a different volume is a new attempt; an attempt that `improved` is not evidence against anything; and the count is scoped to one run, so a real fix does not freeze an action out forever. `recurringFindings` is the free half of the same trigger: a finding class that survived an earlier recorded run is structural, and `index.js` now refuses to print the old unconditional advice "Re-run (the idempotent skip-checks make a re-run cheap)" when its own ledger says a re-run has already not cleared it. Two directions to keep: **a ledger that cannot be read is treated as spinning, not as empty** (refusing an action is recoverable — fix the file and it is available again; spinning is not), and `readLedger` never reports a corrupt or half-parsed ledger as empty (the `readUsableManifest` rule, gotcha 33).

    **The test half.** The first version of `test/test-ledger.js` spawned a real pipeline step with only `AI_API_KEY` blanked — and `SERIES_LOCATION` still came from `.env`. The child read the **live 17-volume series**, reused its committed manifest, and wrote a `translation-report.md` (plus `.json` and a provenance sidecar) at the series root. No model call happened, and the files were harmless empty reports, but a test had modified the corpus it is supposed to be protecting. The rule: **a test that exercises the runner must point at a fixture, not at whatever `.env` says** — blanking the key is not enough, because most tasks never reach the check that needs it (`translationReportStep` calls `getTranslationTarget()` directly and never calls `validateRequiredEnv`). `test/test-ledger.js` now builds a throwaway one-volume series with a committed schema-2 manifest, which is also what keeps the intake agent out of the picture: `readUsableManifest` returns the fixture's plan, so no model call is even attempted, and the suite asserts the words `running the intake agent` never appear in the child's output. Building that fixture surfaced a real gate worth knowing: `validateVolumeIntegrity` requires `integrity.basis` to be **≥ 20 characters** (a gate the intake agent can pass by saying nothing is not a gate), so a fixture that writes `basis: "fixture"` is silently rejected and the intake agent runs instead — offline, it then retries three times with 10 s sleeps and fails 20 s later with a message that points at the fixture's own manifest.
    **The same rule has a second half: a test that pins the context window must pin the output cap
    with it.** `test-fake-backend.js` and `test-translate-stage.js` set `AI_CONTEXT_WINDOW` (16000 /
    32000) and asserted the derived cap, but left `AI_MAX_TOKENS` to whatever `.env` said — and the
    live `.env` now sets it to 131,072. A suite whose pinned window is a twelfth of the cap it
    inherited asked for an answer eight times the size of its own window, so the harness compacted the
    agent session before the first turn, which inserted an extra request at `requests[0]` — and the
    suite asserts both that `requests[0]` is the agent's first turn and that `maxTokens === 4000`.
    The fix is `process.env.AI_MAX_TOKENS = ""` at the top of the suite, **not** `delete`: `dotenv`
    runs at `harness.js:43` and will not overwrite a variable that already exists, so an empty string
    blocks `.env` while `parseInt("")` → `NaN` keeps `envMaxTokens()` deriving from the window the
    suite means to test. Deleting the variable removes the pin and lets `.env` win — which is the same
    failure in a new costume.
