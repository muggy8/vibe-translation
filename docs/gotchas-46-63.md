# Gotchas 46–63 — references and truncation, the cumulative documents, the file tools, and the log

> Gotchas **46–63** of the AGENTS.md gotcha list. The whole list is indexed from AGENTS.md §2.

Hard-won: each one exists because of something that went wrong on a real run.
Part of the ai-client documentation; the entry point is [AGENTS.md](../AGENTS.md).

46. **The cross-chapter audit rides in the `AUDIT_*` batch — do not give it its own phase.** The local containers share one port and a container switch means reloading a model, which is the most expensive thing the translation stage does. The borderline tiebreak and the cross-chapter audit are both second opinions from the same role, so they run inside ONE `withHooks("verify-audit")` batch. Splitting them into two phases would double the switches for every verify round of a 17-volume run for no gain in rigor. Related: it reads `resolvePublishedChapterTexts` — the SAME resolver `mergeVolumeTranslationFiles` uses. If the audit read the drafts directly it would judge one text while `translation.md` published another (accepted polish wins only when it was produced from the current draft).
47. **The targeted repair's trust boundary is paragraph-count equality.** The shortcut maps a source paragraph to a draft paragraph, and the only honest mapping available is "they line up one-to-one" — which is what the paragraph-preserving translation contract produces. When the source and the draft have different paragraph counts the mapping is guesswork, so `planTargetedRepair` refuses and the whole-chapter pass runs. Do not "improve" this with proportional/fuzzy alignment: a wrong mapping deletes good text and inserts text that does not belong, and the deterministic QA is not guaranteed to notice (it checks residue, length and terminology, not which paragraph belongs where). The length-ratio plausibility check is the second guard, and the draft ratchet is the last one.
48. **A glossary dispute is not a finding, and a disputed term is still mandatory.** Two separate rules that only make sense together. (a) When the verifier concludes the GLOSSARY is wrong, the translation was right: the dispute block must not lower the chapter's score, or a faithful translation gets punished for its glossary's mistake — and the retranslate pass would then be told to "fix" a correct rendering. (b) The translator is told the term is disputed AND must still use the canonical rendering: a term the translator is informed is wrong and simultaneously forbidden from changing is a term the QA loop argues about every round forever. The fix happens in the glossary task, which is the only stage that can decide. Consequences: the dispute is recorded per chapter and aggregated by term at the series root; it is part of the per-chapter invalidation key (settling it re-translates only the chapters that actually use the term); and a dispute with no source quote is recorded as `unsupported` — a complaint, not a correction.
49. **`--dry-run` does not prove a live path works.** Two latent crashes in the translation stage were invisible to every dry run and every pure test because the code they live in only runs on a live pass: `retranslate`'s dry-run branch read a variable declared after it (`Cannot access 'cue' before initialization`), and `verify-translate`'s commit phase used `runSettings` that the task never defined. Both surfaced only when the real branch executed. When you add a live-only phase (a report, a queue write, a commit step), give it a test that actually runs it — `test/test-translation-loop.js` and `test/test-disputes.js` stub the model call and run the real code on real files for exactly this reason. The same class bit twice more, in the two phases that run AFTER a stage's model work is paid for: `finishPolishVolume` re-merged the volume with a language pair `polishVolumePhaseA` never handed back (`sourceLanguage is not defined`, on every volume of every run, even one with zero drafts), and `commitVerificationVolume`'s rendering-variant scan used `MERGED_FILE` without importing it (`MERGED_FILE is not defined`, after the whole 133-chapter verify loop). `test/test-artifact-integrity.js` runs both commit phases for real, with no model call, because a commit phase needs no model — which is exactly why it is cheap to test and easy to forget.
50. **"The last existing snapshot" means the last REAL, PUBLISHABLE one.** Each cumulative task publishes its newest per-volume artifact to the series root by walking the volume list backwards and copying the first hit. A plain `fileExists()` check accepts an empty file, and for the wiki it accepts the **scaffold stub** the workflow pre-creates before the author turn — so a run whose last volume failed at generation published `(stub — the merge pass replaces this…)` as the series' living `shared-wiki.md`, and the consistency audit then audited it. All four root copies now use `isPublishableArtifact` (exists AND not empty/stub AND has the SHAPE of the document it claims to be — a Markdown heading or a table), and a snapshot that exists but fails the shape check is **warned about**, not skipped silently. The shape rule is not a size guess: every prompt that writes one of the four specifies a headed Markdown document, so a file with no heading and no table is not that document at any length (observed live: a 164-character planning sentence satisfied the old rule and became the series root's character voice reference — gotcha 58). Per-volume SKIP checks still use `hasRealOutput`: making the skip check stricter would only make volumes regenerate forever, while the copy check is where a bad artifact actually spreads.

51. **Measure a book's prose ACROSS THE BOOK, and compare bytes with bytes.** `checkVolumeSourceShape` is the objective half of "is this a volume?", and it used to (a) sample the first 12 sections at 4000 characters each and (b) reject anything whose file size exceeded 30× that sample. For a real novel the first sections are the cover, the colophon, the caution page and the table of contents, so a 151,245-character book measured **8,419** — and a 10 MB file is 30× that many times over. Observed live: all 17 volumes of a real series were rejected as "art books", the intake failed, and with `ON_TASK_ERROR=continue` every step re-ran it (three attempts apiece) until the `translate` pre-hook switched the container and the intake agent began answering with nothing at all. The honest shape: count the prose across the readable sections (the walk stops as soon as the count clears `DISCOVER_ARTBOOK_MAX_TEXT_CHARS`, so it is bounded, not expensive), and weigh the archive's **non-text payload against its text payload**, both in uncompressed bytes from the zip central directory (`book.payload` from `openEpub` — JSZip knows every entry's size the moment the archive is parsed, so no image is ever decompressed). A real light novel IS mostly image bytes (observed: a 9.6 MB book holding 575 KB of XHTML and 9.2 MB of illustration plates), so "the file is much bigger than its text" is true of every illustrated book and identifies nothing. The art-book verdict needs all three signals: a real image payload (≥ 5 MB), images at least 20× the text pages, and prose thin enough for the archive's composition to outweigh the agent's judgment.

52. **A spine item is a PAGE, not a chapter — chapter boundaries come from the book's own contents list.** The Kadokawa / BOOK☆WALKER "文章型" spec (every volume of the live series) gives every page its own spine item: cover, five half-title plates, a full-colour insert before each chapter, the chapter text, the caution page, the contents page, the author profile, a reader survey, an advertisement, the colophon. Reading the spine literally turned a **10-chapter** book into **35 "chapters"**: the pipeline translated the copyright notice and the contents page, the glossary's research agents spent their turns on blank illustration plates, the chapter-by-chapter fallback burned agent turns on 25 phantom chapters before it reached the real prologue, and `translation-report.md` claimed 25 "EMPTY IN SOURCE" holes in a book that has none. Across the 17 volumes: **554 spine pages → 133 real chapters**. The rules and their reasons are in docs/architecture.md "A chapter is what the BOOK says is a chapter"; the two that are easy to get wrong are (a) an unnamed page must never join an open *packaging* group (volumes 5 and 13 each hide a real 8,000-character story between the contents page and the first chapter's title page — merging it into the cover's fine print deletes it), and (b) **length alone does not decide**: a 568-character copyright notice and a 586-character opening scene are the same size, so the discriminator is what the page DECLARES itself to be (`<body class="p-cover">`, its own `<title>`) — text length is only the tie-breaker for a page that declares nothing. `BUNDLE_SCHEMA_VERSION` 5 forces every stale spine-per-chapter cache to re-extract; artifacts already built under the old split (a volume's `glossary.md`, `chapters.json`, `translation-brief.md`) must be regenerated with `--force`, because they describe a chapter list the book does not have.

53. **Nav hrefs carry anchors — strip them before matching a page.** The same series' contents list points at `xhtml/p-003.xhtml#toc-002`, and the anchor target is the chapter's ILLUSTRATION title page, not its prose page. Keying the nav map with the fragment attached matched nothing, so every real chapter title was lost and every page fell back to its `<title>` — which in this template is the **series title on every single page**, i.e. 35 chapters all named "俺を好きなのはお前だけかよ(1)". `stripHrefFragment` removes `#…` (and `?…`) before the comparison, and the grouping depends on it: the anchor is exactly what re-joins the title page to the body page. Related: `navEntries` (document order, with `inToc` and the declared `epub:type`) is what the grouping reads; the `titles` map alone is not enough, and a `bodymatter` landmark with `inToc: false` ("本編" — "the main text starts here") is a pointer, not a chapter.

54. **A token count belongs to a (text, MODEL) pair — so persist the SCRIPT MIX, not a token count.** The instinct is to measure a book once at intake and stamp its size on the manifest. That is wrong here: the translation stage runs up to four different models (translate / verify / edit / audit), each with its own tokenizer, and on this machine they all share one port and one model alias (`local`, gotcha 22). A number stamped by the intake agent is a lie the moment the auditor budgets a prompt with it. So the split is: `scriptMix` (CJK characters vs everything else) is a property of the TEXT and is persisted in the bundle cache (`BUNDLE_SCHEMA_VERSION` 6, whole + per chapter, so a cached extraction never has to be re-read); the COEFFICIENTS are a property of the MODEL and are measured per endpoint at stage start, where the hooks have already switched the right container in. Measured, not assumed: a whole Japanese light novel is **0.588–0.622 tokens per character** (128,744–176,201 chars → 75,757–109,628 tokens across the 17 volumes), and the old coefficients (1.0 per CJK char, 0.35 per other) over-counted by **1.42–1.47× on both Japanese AND Latin text** — which is why the prompt budget threw away roughly a fifth of the reference material it could have kept. Consequences: (a) `estimateTokens` must NOT bill the 52-token chat template, because `fitPromptBudget` estimates per BLOCK and would charge the same overhead five times — it is subtracted once, in `tokenBudgetFor`; (b) the calibration key `baseUrl|model` cannot distinguish two containers that advertise the same alias, which is why `TOKEN_CALIBRATION_MAX_AGE_HOURS` exists — the age is what eventually re-measures a swapped model; (c) a probe is a real request (this server has no `/tokenize` — `/tokenize`, `/v1/tokenize`, `/api/tokenize`, `/num_tokens` all 404, and `max_tokens: 0` is IGNORED, so a probe must use `max_tokens: 1`), which is why the pipeline calibrates the model once and derives every volume's count from character counts instead of probing each volume; (d) calibration is FAIL-SOFT — a probe that cannot run leaves the built-in coefficients, which over-count, so token accounting can never be the reason a run dies.

55. **The whole→chunked fallback triggers on ONE tagged error class, and a bad acceptance score is deliberately not it.** A whole-installment pass is the cheap, cache-friendly path, so when it turns out not to fit, retrying the same volume chapter by chapter is a genuine repair rather than a retry of the same mistake. But "on any error, try chunked" is a trap: a hang, a malformed tool call, a dead container and a missing previous artifact are not size problems, and chunking them costs the whole volume again to fix something chunking cannot fix. So `tooBigForOnePassError` (the mirror of `structuralError` in `configs/shared.js`) is tagged at exactly three sites in `harness.js` — the server refusing a request because prompt + `max_tokens` exceed its context (`tagSizeOverflowError` matches the phrasings, so no task has to string-match a server's error text), an agent turn truncated while writing a file, and a tool-less call that hit the output cap — and `runVolumeWithModeFallback` acts on nothing else. **A low ACCEPTANCE score is not a size failure and must never auto-switch the mode**: it is the QA loop's problem, it is stochastic, and switching on it would make which mode ran — and therefore what the artifacts look like — irreproducible between runs. The fallback also wipes the failed attempt's outputs AND its `*-rolling-state.json` before retrying, because the two modes leave different files behind and the chunked path would otherwise read a partial artifact, a research skeleton full of `- (pending)` lines, and scores recorded for documents that no longer exist (gotcha 3, gotcha 50). It runs ONCE: a second failure reports both attempts rather than looping. And a whole-mode failure is worth READING even when it recovers — the size check said the volume fitted, so either the estimate is off for that model or the cumulative reference outgrew the allowance; the fallback message says so and names `SOURCE_CHUNK_SAFETY_FRACTION`.

56. **A whole-mode pass carries the whole book in the agent's own session, and the request-window arithmetic cannot see that.** In whole mode the author agent reads the entire volume through one `readFile` call (OpenHarness's `NodeFsProvider` default cap is 10 MB, so a 150 KB book arrives in one call — roughly 100k tokens), and that text then sits in its session alongside the system prompt, the previous volume's cumulative reference, and the file it is writing. The session used to auto-compact at `AI_CONTEXT_WINDOW`, and compaction is LOSSY: it is how "the agent quietly stopped honoring the honorific rules" first shows up — as a worse artifact, not as a failure. **It no longer compacts at all** (auto-compaction is switched off on every agent handle — gotcha 78), which converts this failure from a silent one into a size error the mode fallback repairs; the warning below is still worth reading, because a whole-mode pass still carries the whole book in the agent's context, and nothing can compact it for it. `planProcessingMode`'s fraction check bounds the REQUEST; it cannot bound the session. That is why the decision also prints a warning when the whole volume alone exceeds half the window, and why the honest reading of a whole-mode run is the artifact quality, not just the exit code. If a volume trips it repeatedly, `--chunked` is the correct answer for that volume — not a bigger window.

57. **A character constant cannot see the answer, so it split half the series for no reason.** `TRANSLATE_CHUNK_CHARS = 24000` was the last size decision in the pipeline still measured in characters, and it applied identically whether the model had a 262,144-token window or a 32,000 one, whether thinking was on or off, and whether the chapter was Japanese or Latin. Measured against the real 17 volumes: it split **55 of 133 chapters**, while the largest chapter (49,840 characters = 34,716 tokens) leaves 161,840 tokens of the window free for the references after its output reserve — one call, no seam. The token plan splits **0 of 133** under the normal settings and **30 of 133** when `TRANSLATE_THINKING=high`, because reasoning tokens are billed as output and must fit the same cap as the translation; the character rule would have split the same 55 either way, which is the tell that it was not measuring anything. Two consequences for anyone changing this: (a) the **output cap is subtracted twice on purpose** — once in the admission limit (the server adds `max_tokens` to the prompt when it decides whether to accept the request, gotcha 36, so it is gone from the window whether or not the model uses it) and once as the ceiling on the expected answer (the generation is cut off mid-chapter if the answer exceeds it) — and (b) the conversion from tokens to characters uses the chapter's OWN measured characters-per-token, never a per-language constant, because the same token allowance is worth ~2.8× more Latin characters than CJK ones (gotcha 54). `TRANSLATE_CHUNK_CHARS` is still honoured as a hard ceiling when an operator sets it explicitly — arithmetic does not overrule a deliberate limit — and `translateChunkCap()` returning `null` is what distinguishes "unset" from "the default".

58. **A chat reply is not evidence of an artifact, and one reply is never two documents.** `assertWroteWithFallback` recovers an agent that produced its output in its chat reply instead of calling `writeFile` by writing that reply to disk. Unconditional, that is a corruption path, and it was observed live end to end: an author agent could not read the previous volume's character-voice reference (the file tools cut every line longer than 2000 characters, and a compiled reference holds one long line per character — 2,344 at volume 02, 2,863 at volume 03), so it tried to split the long lines to see them, never restored them, ran out of turn budget, and its final reply was the sentence *"I need the full content of two very long lines in the previous reference. Let me temporarily split them…"*. The fallback wrote that 164-character sentence into **both** expected outputs (`character-voice.md` and `pov-map.md`). 164 characters of English prose is neither empty nor a `(stub —` marker, so it passed `assertRealOutput`, the acceptance loop, the validation report, and the last-good-volume copy walk — and became the series root's character voice reference. Three rules now stand between a no-op turn and a published artifact, and they are all load-bearing:
    - **`looksLikeArtifact`** (utils/fs.js): the reply must be at least `AGENT_RECOVERY_MIN_CHARS` (1000) characters AND hold a Markdown heading or a table — the shape every prompt in this pipeline already specifies. Size alone is not evidence, and neither is confidence.
    - **One reply, one file.** The fallback writes only when exactly ONE expected output is missing. A two-file gap is repaired by the recovery turn, never by duplicating one reply across both artifacts.
    - **Refusing is not fatal.** The call still returns `true`, so the caller sends the recovery turn, and `assertRealOutput` after it is the hard stop. The asymmetry to remember: a missing file fails loudly and is picked up on a re-run, while a plausible-looking wrong file gets audited, published, copied to the series root, and injected into the next volume's prompts. Consequence: with `AGENT_RECOVERY_ENABLED=false`, a two-file gap now FAILS the volume instead of publishing a pair of wrong artifacts — turning recovery off means the hard stop is the only thing left.
    The other half of the fix is the read caps (`AGENT_MAX_LINE_LENGTH` 8000 / `AGENT_MAX_READ_BYTES` 65536 in `createGatedFsTools`): an agent that can read the artifact it is required to preserve does not start reconstructing it from memory. Raising the byte cap is also a token fix — reading a 150 KB artifact in five paged calls re-bills the growing transcript five times, which is a large part of why the character-voice stage cost 173M tokens for five volumes. Do not "improve" this by writing the reply anyway when the gate refuses: the gate exists because the pipeline cannot tell a document from a sentence about a plan by checking that the file is non-empty.
    - **The root copy is where it would have spread.** The four series-level copies walk the volume list backwards and publish the first hit, and the audit, every later volume's prompts and the translation stage read that copy. They now use `isPublishableArtifact` (gotcha 50): real AND the shape of the document it claims to be, warned about rather than skipped silently. The per-volume SKIP checks deliberately keep the looser `hasRealOutput` — a stricter skip rule only makes volumes regenerate forever, while the copy rule is where one bad artifact actually reaches the series.

59. **The reasoning budget is a shared resource, and an empty reply is what starvation looks like.** Measured on the live 17-volume run: 203,961,788 input tokens, 173M of them in the character-voice stage, 22 calls that answered with nothing, and one glossary call that spent 131,072 reasoning tokens and produced **0 characters** of content (`finish_reason=length`). A reasoning phase that consumes the whole reply budget does not produce a worse answer, it produces no answer — and the pipeline's guards can only report that. The rule that keeps it bounded: **a call whose job is to produce a number samples like a grader** — `JUDGE_TEMPERATURE` plus `STAGE_THINKING_LEVEL` (default `medium`), through `judgeThinking()` (configs/shared.js) for the calls outside the translation stage and `stageThinking()` (which now delegates to it) inside. The four pre-production acceptance graders used to inherit the AUTHORING level (`AI_THINKING_LEVEL`, default `xhigh`) because `stageThinking` never reached them — that is the shape the 22 empty replies came out of. What still runs at `AI_THINKING_LEVEL`, deliberately: the authoring agent turns (author / validator / feedback / intake / audit agent) and the extraction one-shots, because an agent writing a 150 KB artifact is the call that needs the thinking, and `AI_THINKING_LEVEL` is the per-series knob for it (gotcha 1). The tell when a run is starving: `reasoning=` next to `content=` in `.logs/*/summary.log` — a call whose reasoning dwarfs its content is the one to turn down. The prompt audit's `judging-dialect` rule reports any grading call that samples like a writing call, so the gap cannot come back quietly.

60. **The file tools are stricter than the way a model reaches for them, and the schema cannot catch it.** `dirPath` is `z.string()` and `glob` is `z.string()`: a file where a folder belongs, or a wildcard where a suffix belongs, passes validation and only fails (or silently succeeds at nothing) when the tool runs. Measured on the live series' logged runs — 1030 grep calls: **40 died with `ENOTDIR: not a directory`** and **398 searched for nothing and reported "No matches found"**. Three separate mismatches, all agent-facing:
    - **`grep`/`listFiles` take a FOLDER, and the tool walks it.** The pipeline's own prompts caused the crash: `glossary.js` names one file and says "read it selectively with readFile/grep", so the agent passes that file as `dirPath`. `readFile` takes a file; `grep` does not. Recoverable (the model sees the error and retries) but every one is a wasted step out of a validator's capped budget.
    - **`grep`'s `glob` is a filename ENDING** — the library's implementation is `file.endsWith(glob)`, and its own test uses `glob: ".ts"` — but the word "glob" makes every model write `"*.md"`. That matches NOTHING and answers `No matches found for /*.md/.` **This is the worse half**: it is silent, and an agent that searched `*whole.md` and got nothing reports the term as absent from the source. A wrong artifact, not a wasted call.
    - **The library's binary-file list does not know `.epub`.** A grep over a volume folder (which holds the staged book) or the series root (which holds all 17) decoded zip bytes as UTF-8 and matched the noise; `readFile` on a staged book answered mojibake. The intake brief already promised "the file tools REFUSE .epub paths" — it was enforced only for `filePath`, so `grep(dirPath: "book.epub")` walked straight through it.

    The fix is three-layered, and all three layers matter: the **tool descriptions** state the contract (the description is the half the model reads), the **input is repaired** and the repair is reported in the answer's `status` line so the agent learns instead of being quietly redirected (`applyFsToolContract` + `normalizeDirToolInput` in harness.js), and the **fs provider refuses an archive as text** (`withBookAwareReads`) — which is also what the library's grep wants, since it catches a failed read and skips the file. Two invariants to keep: the normalization runs INSIDE `wrapToolsWithApproval`, so the approve gate always judges the agent's ORIGINAL path (a repair can never smuggle a denied path through); and `editFile`'s parameter is `oldString`, not `oldText` — the prompts used to say `oldText`, and a model that obeys the prompt instead of the schema gets `Invalid input for tool editFile`. Pinned in `test/test-artifact-integrity.js` **both ways** (the raw library still crashes on a file, still matches nothing for `*.md`, still reads an epub as text; the tools an agent is handed do not) plus `test/test-intake.js` for the gate at `dirPath`. Related: a regex from another dialect (`(?i)vice`) used to throw a raw `SyntaxError` at the agent; it is now answered with the flag the tool actually has (`ignoreCase`).

61. **An agent transcript without tool results is a transcript that cannot explain itself.** `consumeEvents` handled `tool.start` and `tool.error` but had no case for the library's `tool.done`, so 526 logged agent turns recorded every tool CALL and none of their answers — while AGENTS.md promised "tool calls + results". `escapeInline` was the other half: it ran `String()` on the tool input, which answers `[object Object]`, so even the calls were unreadable in the chat log (only `summary.log`, which uses `summarizeInput`, showed the real arguments). The distinction that was being lost is the one this pipeline most needs: "the search ran and found nothing" versus "the search never ran" (see gotcha 60) look identical in a log that records neither. Pairing is by `toolCallId`, not "the last call seen" — a step fires several calls at once, and an error used to be pinned onto a call that had succeeded.

62. **A failed model call reached `consumeEvents` as an event, and nothing looked at it.** Found by running the real task against the scripted endpoint (`test/fake-backend.js`), not by a live run. When the endpoint fails — a 500, a refused request, a provider error — the AI SDK does not throw into the `for await`: it emits an `error` part, and openharness forwards it as an `error` event and then closes the turn (`turn.start` … `error` … `turn.done`) WITHOUT ever emitting `done`. So `result.result` stayed `null`, `consumeEvents` only threw on `result.result === "error"`, `result.error` was carried and discarded, and `runOneShot` reported **"The model returned no content"** for every failure. Three consequences, all real:
   - `tagSizeOverflowError` never saw the server's own "prompt (4337 tokens) + max tokens (262144) exceeds the context" wording, so `tooBigForOnePassError` was never tagged on the one-shot path and **`runVolumeWithModeFallback` never fired for the single failure it exists to repair** (gotcha 55). The whole-installment pass simply failed, and the log blamed the model.
   - An overnight run's log said the model answered with nothing when the container was not running. The actionable sentence was in `result.error` and was thrown away.
   - The non-streaming fallback ran for a request the server had already refused for being too large — a second doomed request, at the same size, guaranteed to fail the same way.

   `consumeEvents` now throws `result.error` whenever the stream ended without a normal completion (`complete` / `max_steps`), and `runOneShot` skips the non-streaming retry when the error is already tagged as a size failure. The rule to keep: **an event loop that records an error must also surface it** — a `result` object with an `error` field nobody reads is how a pipeline reports a healthy model for a dead one. Pinned in `test/test-fake-backend.js` (the `tooBig` / `serverError` / `hang` scenarios, plus the scenario that hands the real tagged error to `runVolumeWithModeFallback` and asserts the volume actually re-runs chapter by chapter — the half `test-tokens.js` cannot reach, because there the error is hand-built) and in `test/test-translate-stage.js` (the `dead` scenario, which asserts the run log carries the server's message and specifically does NOT contain "returned no content").

63. **A scripted model server that lives in the test process deadlocks with a synchronous child spawn.** `test/test-pipeline-loop.js` has to run each task in its own process (task modules read `SERIES_LOCATION` at module load) while the scripted endpoint it talks to is an HTTP server in the PARENT process. `spawnSync` parks the parent's event loop for the whole life of the child, so the server accepts the connection and then never processes a single request. Every stage hangs until `AI_CALL_DEADLINE_MS` fires and the harness reports "the agent turn made no progress for 2 min and was aborted … the endpoint is likely hung or the model container died" — a message that blames an endpoint which was, in fact, blocked by the test's own runner. The tell that separates the two: **a hang with zero requests recorded**. A real dead endpoint still gets the request; a blocked server never receives one. The fix is to await an asynchronous `spawn` (`runStageAsync`). The rule to keep: anything that must answer a request while another process runs has to be awaited, never blocked on — and when a stub-driven run reports a hung endpoint, check the request count before believing it.
