# Gotchas 70–82 — the delivery layer: the option filter, the resume triage, the run lock, the acceptance test, the two support teams, the loop, the uncapped turn, the default source folder, the paths a split moves, the ids a model has to copy, and the glossary window that could not read furigana

> Gotchas **70–82** of the AGENTS.md gotcha list. The whole list is indexed from AGENTS.md §2.

Hard-won: each one exists because of something that went wrong on a real run.
Part of the ai-client documentation; the entry point is [AGENTS.md](../AGENTS.md).

70. **A rule about what an agent may choose has to sit on the thing that offers the choice, and a request for help must not state the result it wants.** The delivery-manager design gives an agent authority to act on a run without ever reading the code, and the moment it stops working it calls in the teams that CAN read the code. Two things about that conversation are load-bearing, and both come from volume 15 (gotcha 68).
    - **A ticket asks a question; it never states the result it wants.** "Make volume 15's glossary pass" is not a request for diagnosis, it is an instruction handed to people who know the code — and the cheapest way to satisfy it is always the one that removes the *finding* rather than the *fault*. In that incident the finding was a gate correctly refusing a glossary that had GROWN from 445 terms to 460, and the cheapest answer was `GLOSSARY_CARRY_FORWARD_GUARD=false` — the exact setting under which 457 terms once vanished with no error (gotcha 64). So `validateTicketShape` refuses the demand shapes (a sentence that commands, a clause that names the finding disappearing as the goal, a summary with no question in it) and each refusal says what to write instead. Be honest about what this is: a **shape** check, not a mind reader. It catches the forms a demand actually takes; the acceptance test (comparing the deliverable before and after) is what catches a demand phrased cleverly.
    - **The banned-option filter sits on the option generator, not on the chooser.** A manager given a menu picks the cheap item on it. That is not a flaw to be fixed by instructing the manager to choose wisely — instructing it is the same rule written in prose, where nothing enforces it. So `attachOptions` runs `optionIsBanned` on the diagnostics team's reply and refuses, in code: disabling a carry-forward guard, `--allow-fail` / `--allow-no-glossary`, lowering `PASSING_SCORE` or any acceptance threshold, deleting `.rejected` files or reports, editing `hooks/`, declaring an artifact expectation away, flipping an `ON_*` run policy to `skip`, and disabling the ledger. Every refusal names where it goes instead — **the account owner**, the only role that may un-check a guard — and the refused option is KEPT on the ticket, because a dropped option looks like it was never thought of and the complaint about a guard is information.
    - **The filter is narrower than "is this a good idea", and that is deliberate.** `Add the old spelling back as a second row` is not banned: it manufactures a duplicate, which is a judgment about the deliverable, not a guard being removed, and the thing that rejects it is the before/after comparison, not this filter. `test/test-tickets.js` pins that split rather than smoothing it over, and pins the false-positive half too — seven legitimate options must pass the filter, because a filter that refuses everything is the filter that gets switched off (gotcha 65's lesson in its general form). Related rules: a ticket's "already tried" list is read out of the ledger rather than asserted from memory, so a spin cannot be laundered into a fresh request; and a ticket closes only as `improved` / `unchanged` / `worse`, never as `finding-gone`.

71. **A triage that reads a half-built run has to tell "a gate fired" apart from "work is missing" — and a declared artifact name is a template, not a file name.** `utils/resume.js` was written against a spec and then run against the live 17 volumes, and the live run found four bugs in it in under a second, none of which a fixture built by hand would have found. What it proposed first: **wipe volume 02's glossary and cascade 02→17** — throwing away thirteen volumes of accepted work, because a `glossary.md.rejected` was lying in volume 02's folder. Volume 02's glossary is complete; the `.rejected` is evidence from the run that got stopped, and that volume was rebuilt afterwards. Four rules, each one the fix of one of those bugs:
    - **Damage and evidence are different findings, and only damage picks the resume point.** `quarantine-present` is HIGH in `utils/postmortem.js` — correctly, a gate refused something and nobody read it — but it is not a statement that the work is unfinished. So `readWorkingState` splits the HIGH findings, and a step whose required output is complete while its evidence survives gets status `quarantined` and verdict `evidence`: *read it before running anything*. The split is written fail-closed — a HIGH finding counts as damage **unless it is explicitly listed as evidence**, so a finding kind added later to `utils/postmortem.js` cannot become invisible here by omission.
    - **A quarantine belongs to the artifact it names.** `utils/artifacts.js` declares ONE pattern (`QUARANTINED_CUMULATIVE`) for all three cumulative gates, so pattern-matching alone says a `character-voice.md.rejected` is glossary's evidence — and then the "the gate removed this output" rule fires for a volume whose glossary gate never fired, which is the wrong reason to refuse a rebuild. `quarantineBelongsToStep` strips the `.rejected` suffix and asks which step declares THAT file.
    - **`{installment}` is a placeholder, and comparing it to a directory listing never matches.** `jump-in-wiki-validation-{installment}.md` was reported missing on every volume of a series that had it, and `declaredOutputsFor` put a literal `{installment}` into a **delete list**, where it deletes nothing — which is worse than an error, because the wipe looks like it happened. `resolveDeclaredName` is now applied everywhere a declared name meets the disk.
    - **When the gate removed the output, a re-run is the spin, and the plan has to say so.** Volume 15 is missing its glossary AND holds `glossary.md.rejected` in the same folder. Re-running the step rebuilds the file and runs the same deterministic gate over it, producing the identical quarantine (gotcha 68). So that shape becomes `open-ticket`, with the reason naming the identical quarantine out loud — a refusal that does not name the spin just looks like caution, and caution is what gets switched off. The same escalation applies to a FAIL audit verdict (re-auditing unchanged artifacts reproduces the FAIL) and to a finding the ledger says already survived a recorded run.
    Two silent no-ops surfaced while testing the last one, and they are the general lesson of docs/delivery-layer.md and gotcha 67: `recurringFindings(entries)` was called **without a run id**, and its own body requires `runs.has(run)` — so it returned `[]` forever, and the "this finding survived a run" warning could never fire; and the renderer read `r.kind` from an object whose field is `finding`, so even when it did fire the sentence would have named nothing. A check that can never report is not a check. For a resume triage the run it means is **the newest one recorded** (`entries[entries.length - 1].run`), because the triage has no run of its own — it is reading what previous runs left.
    The fixture half is worth as much: seeding a "complete" series from `STEP_ARTIFACT_SPECS` itself is the right way to build one (the fixture and the declaration cannot drift), but `discover` **declares the plan of record as one of its outputs**, so the seeder overwrote the fixture's committed manifest and the triage correctly reported that there is no usable plan (gotcha 33). And `validateDiscoveryBlock` wants `discovery.confidence` as an **object of 0–1 numbers**, not a number — a fixture whose plan does not validate is a fixture with no plan at all, same as `integrity.basis`'s 20-character floor in gotcha 69. Finally: `postMortemDir()` is where the ledger lives, so a resume test that does not set `POSTMORTEM_DIR` is reading the real series' history, and a finding recorded there changes what the test asserts.

72. **A manager that can act has to know whether something else is writing, and its own actions have to be countable — or every guard built on top of it is decoration.** Act mode turns "the manager proposes" into "the manager does", and that turned three things that were safe by accident into things that had to be built.

    **The collision.** A manager with authority to re-run a step can start a step while a run is already working on the same folders, and the damage is invisible to every check in this file: the artifact ends half-built by one process and half by the other, and "is the file there?" says yes. So `<POSTMORTEM_DIR>/run.lock` says who is running, and `index.js` plus **every** gulp task take it before doing anything — wrapped outside `withHooks`, so a refusal costs no model container switch (gotcha 22). Nesting is counted, because the default run holds one lock across its nine in-process steps while `index.js` spawns gulp children that inherit `INDEX_RUN_ID` and join it; only the writer deletes it. Two directions, and getting them the wrong way round is the bug: the lock is **advisory to the pipeline** — a lock file that cannot be written warns and continues, because a bookkeeping file must not be the reason a 12-hour run dies — and **binding to the manager**, which treats "I cannot tell" as "no", because deciding whether it is safe to act is its whole job. Liveness is the pid, and a pid this machine cannot check (a lock written on another host) is treated as *in progress* with the file to delete named out loud: guessing "probably stale" is how a half-written volume gets a second writer. The lock lives in `POSTMORTEM_DIR`, not per series, so two concurrent runs of two different series collide — the answer is a separate `POSTMORTEM_DIR` per series, and the refusal says so in the sentence it prints.

    **The count.** Act mode records what it did, and it must record it under the **newest recorded run**, not a fresh id per invocation. A manager that invents its own run id each time is uncatchable: the anti-spin gate counts per run (gotcha 69), so every attempt would look like the first. A genuinely new `npm run pipeline` run makes its own id, and that is where the count resets. Two halves of the same rule fell out of the tests: `appendLedgerEntry` used to write `String(null)` for a null volume, storing the four-character string `"null"`, and `matchesKey` compares a step-level entry against a step-level key — so a whole-step action (`re-audit` on `consistency-audit`, which names no volume) **never matched itself** and the gate silently stopped counting the exact case it exists for; and a `re-run-step` on a step that is only in the plan because the resume step's fix invalidates it had no finding to key on, so the ledger refused it as "half-specified" — seven spurious tickets on a fixture with nothing wrong with them. A complete step in a resume plan now **inherits the finding the whole plan is a response to**, which is honest: the whole sequence is one response to one finding.

    **The sequence.** A resume plan is not a list of independent suggestions. If the step where the run stopped is escalated to a ticket, the seven steps listed after it are conditional on that ticket being answered, and running them spends a real run's worth of model calls on a foundation this manager could not fix — so act mode executes nothing in that shape, and stops at the first refusal or failed step. Related refusals, all for the same reason: no `--dry-run` passthrough in act mode and no `--no-write` with `--mode=act` (exit 2), because a rehearsal that records its interventions poisons the ledger that is supposed to catch the spin; and a Tier C move is refused **at execution time**, not only in the proposal, because the proposal is a document and execution is the thing with consequences. `test/test-delivery-act.js` pins all of it against real fixtures and real step-runner children, including the half that matters most: a refusal leaves the folder listing byte-for-byte as it was, because a refusal that wiped first is indistinguishable from a fix.

73. **"Did it help?" has to be answered by the deliverable, not by the finding — and a measurement that reads a gate's verdict can be satisfied by switching the gate off.** Act mode's first verdict rule was a per-volume count: how many of the step's volumes had their required files before, and how many after. It was replaced by `utils/delivery-verify.js`, and the reason is a case the count could not see at all. The test that exercised the plumbing wiped volume 02's glossary and ran the step with `--dry-run`, which rebuilds nothing. The count reported `unchanged` — volume 02 was missing files before and missing files after, so nothing had crossed the line — while the deliverable had actually **lost a glossary that was there**. A manager that reports a clean run after deleting accepted work is worse than a manager that refuses. Four rules, and each one is a distinct failure mode:

    - **A regression vetoes an improvement.** The planted test "fix" finishes the step (every declared file written, the next triage reports nothing to do) and writes a glossary with the term rows missing. It is recorded as `worse`, with the damage named. This is the case `utils/tickets.js` deliberately does **not** ban — `Add the old spelling back as a second row` is a judgment about the deliverable, not a guard being switched off (gotcha 70) — so the thing that has to reject it is this comparison. A rule that netted the two out would call it a win: the finding gone plus a step completed against one smaller glossary is a comfortable majority in favour.
    - **A gate's verdict is not a deliverable signal.** `consistency-report.md`'s PASS/FAIL, the four validation reports, the quarantine counts and the post-mortem's own findings are all excluded from the measurement. Every one of them moves for free when the check is disabled, which is exactly the cheapest answer a ticket gets (gotcha 70 again). Only facts about the **content** the pipeline produced are measured — how many term rows the glossary carries, how many `### Character` sections the voice reference holds, which `## ` style categories survive, how many chapters `chapters.json` hands the translator, and the publish report's own buckets. That is the difference between "the complaint stopped" and "the book got better", and it is why a weakened guard cannot be accepted as a fix even when it is honestly reported as one.
    - **An incomplete measurement is reported, never guessed.** A file that could not be read (a directory where the glossary was, an artifact over the read cap) makes that step's content signals *not comparable* — not zero. `fingerprintFiles`' rule in `utils/fs.js` is the same rule ("an unreadable file fingerprints as `missing` so a read error cannot masquerade as 'nothing changed'"), and the direction matters: treating a read failure as an empty document reports a permissions problem as a loss of terminology, which is the direction of error that gets accepted work deleted. Two related honesty rules: a corrupt `glossary-disputes.json` is not "the disputes were settled", and the median verification score is compared only when both sides graded the **same number of chapters** — a book that gained a chapter is a different book, and averaging across it is not a measurement.
    - **The protected quantity is the one the pipeline's own gate protects.** Glossary terms, `### Character` sections, `## ` style categories: the same three halves `GLOSSARY_CARRY_FORWARD_GUARD` / `VOICE_CARRY_FORWARD_GUARD` / `STYLE_CARRY_FORWARD_GUARD` guard (gotcha 64/65/68). And where those gates deliberately stop, so does this: the style guide's **rule count** is `veto: false`, because "a guide that says the same thing in fewer words is not damaged" is already the codebase's answer, and a measurement that guarded a different quantity than the gate does would report a different series of failures than the one the pipeline can actually see. A reworded character heading moves nothing here either — deciding whether a rename is a loss is the carry-forward gate's job (gotcha 68), not a heading count's.

    Two supporting changes came out of building it. The publish report is now read through **one** reader — `readTranslationReport` + `summarizeReportRows` in `utils/translation-report.js`, the module that writes the file — so the resume triage and the before/after comparison cannot count one report two ways; and the ledger stores the `signals` account next to the verdict, because a verdict with no numbers beside it is a verdict nobody can argue with afterwards, least of all the diagnostics team who is the reader this whole layer exists to serve. A ticket closes through the same comparison (`closureFromComparison`, reached from `delivery.js`'s `closeTicketOnDeliverable`), so the manager cannot record `worse` in the ledger and close the ticket `improved`. One measurement bug worth remembering: `countHeadings` was a prefix test, and `"### Character".startsWith("##")` is true — so every level-3 heading counted as a level-2 one, and then **none** of them counted when level 3 was asked for. A heading is its level marker followed by a space.

74. **A read-only agent needs its guarantee twice, and its answer needs the same filter as its question — plus a rule about what a support team is allowed to have actually read.** The diagnostics role is the first agent in this pipeline whose *whole job* is to look at the code without changing it, and three things turned out not to be automatic.

    **The two layers, and which one actually fires.** `createGatedFsTools` builds five tools and an approve gate. Handing that whole set to a read-only agent and letting the gate say no is one layer; handing it only the three read tools is another. Both are needed, and the reason the *record* is the hard part is that when the tool set is the one that refuses, the gate is never consulted at all — the provider answers `Model tried to call unavailable tool 'writeFile'` before the call reaches the sandbox, so the gate's own refusal log is empty and a naive `writeAttempts: gate.refusals` reports **"the team did not try"** for the common case where it tried and the tool set said no. `collectWriteAttempts` merges both sources (the gate's log, plus the turn's recorded tool calls whose name is a mutating one) and labels which layer stopped each. The same two-layer shape is what gotcha 8 already pins for `deleteFile`; this is that rule applied to a role whose entire contract is "look, don't touch". And the refusal must reach the model, not just the log: a denied call surfaces as a tool error and the loop continues, which is what lets the turn finish with an answer instead of dying on a refusal.

    **`AGENT_TOOLS_NOTE` is a promise about writing.** The shared note appended to every agent-mode system prompt names five tools and tells the agent to write its output with them. For a read-only role that is not a slightly-off hint, it is an instruction the role cannot obey, and a model that follows it spends capped steps reasoning about a write it is not allowed to do (gotcha 8's `deleteFile` transcripts are exactly that shape). So the diagnostics prompt carries its own `DIAGNOSIS_TOOLS_NOTE`, appended in code like every other mode-specific note (AGENTS.md convention: prompt files stay mode-agnostic), and it says what the role has, what it must not do, and the exact JSON shape to answer in.

    **A diagnosis is a claim about reading, so check the reading.** `crossCheckReads` compares the reply's `read` list against the turn's real tool calls, and the two rules that keep it from being a false-positive machine are the ones easy to get wrong: a `grep`/`listFiles` call names a **folder** and reads everything inside it (gotcha 60), so a claim about a file under that folder is *not* "cited but never opened"; and a call that **errored** covers nothing, so counting it would let a reply cite a file it only managed to fail to open. Both directions were wrong in the first version, and a check that accuses an honest diagnosis is a check the next incident routes around (gotcha 65's lesson again). The same honesty applies to the outcome-only rule: an option whose only stated check is "the finding disappears" is **flagged**, not refused, because the thing that rejects it is the before/after comparison of the deliverable (gotcha 73) — and the flag has to be stamped by `filterOptions`, on the way onto the ticket, or it exists only in the in-memory reply and never reaches `tickets.md` or the manager who has to read it.

    **The filter is the door, so make it the only door.** `recordDiagnosis` calls `attachOptions` internally. That is not tidiness: if the manager-side code could write a diagnosis without going through the filter, the filter would be a suggestion (gotcha 70). Two consequences worth remembering: when every offered option was refused, the ticket keeps status `answered` and gains `noUsableOptions` rather than inventing a new status — and `recordDiagnosis` writes `noUsableOptions: false` explicitly when usable options survive, because "absent" and "false" must not mean the same thing on a ticket a human reads. And the manager's side of the conversation is validated on the **answer**, not the question: the team may ask anything it needs to, but a reply may cite only what a customer is allowed to see, so `.logs/**`, `*.js`, `system-prompts/`, `hooks/` and `utils/` are refused at the point where the boundary would actually leak — with the refusal naming what the manager *may* look at, because the useful failure is the one that produces a usable second answer.

75. **A role that may change the code needs its boundary enforced twice, its claims checked against the disk, and its unfinished work reported as unfinished — and the record is where all three actually get decided.** The dev team is the last role in the delivery layer and the only one that writes, and building it produced four lessons that were each a bug first.

    **Both layers fire, and only one of them leaves a log.** `patchFsTools` hands the agent five tools and an approve gate that refuses `deleteFile` and every banned path. But a tool the harness never advertises never reaches the gate: the provider answers `Model tried to call unavailable tool 'deleteFile'` and the gate's refusal list stays empty. So the record has to be assembled from both sources, exactly like `collectWriteAttempts` for the read-only role (gotcha 74) — and the first version of `collectPatchWriteAttempts` over-corrected: it counted *every* mutating tool call the gate had not refused as a tool-set refusal, which reported the patch's own **successful** `editFile` as "not offered to this role at all". The fix is the third argument, `advertised`: a call counts as a tool-set refusal only when its name is NOT in the list the role was actually handed. The general rule: **a write that succeeded belongs in `actualChanges`** — the tree fingerprint — **not in the refusals**, and a report that mixes them makes a working patch look like an attempted break-in. The default `[]` keeps the read-only role's assumption intact, which is what `utils/diagnostics.js` relies on.

    **The harness gives an agent no shell, so "run the tests" is the machine's job.** A brief that told the team to run `npm test` would spend capped steps discovering it cannot, and a proposal that claimed it had run them would be unverifiable — the same shape as gotcha 8's `deleteFile` transcripts, where agents burned budget reasoning about a tool that does not exist. So `DEVTEAM_TOOLS_NOTE` says plainly that there is no shell and that the machine runs the checks, and `REQUIRED_CHECKS` + `runChecks` run `npm test` then `npm run pipeline-loop` from the CLI, through a shell because `npm` is a `.cmd` shim on Windows, with a 30-minute ceiling and the tail of the output stored. Two honesty rules came out of that: `normalizeChecks` takes the command from the table and never from the caller (an unpinned id is dropped, so the verdict reports it MISSING instead of trusting whatever was handed in), and **a check that never ran is reported as missing, not as failed** — "did not run" and "ran and returned 1" are different facts and the report prints them on separate lines. `judgeChecks` keeps them apart, and a failing re-verify moves a `verified` patch back to `proposed` rather than leaving a stale green badge on it.

    **The banned-path table is necessary and not sufficient, and its refusals have to name the rule.** A patch may not edit the guard tables, the tests that pin them, `hooks/`, `.env`, the machine state or the corpus — enforced on the file tools during the turn AND on the proposal afterwards, because a team that gets past one layer has not been stopped. Three details are load-bearing. (a) **Specific rule first, catch-all last:** `hooks/pre-glossary.sh` must be refused as `edit-hooks`, not as "corpus", because the refusal is the information the team uses to write a second proposal. (b) **A path that cannot be normalised into the project is banned, not allowed** — and `normalizeProjectPath` resolves an ABSOLUTE path against the root it was given, because `renderTicketForDev` names the project root in full and an agent that used the path it was handed was being refused for every legitimate write. A path genuinely outside the root still returns null. (c) **The project-source test is a whitelist, not a blacklist:** `ai-client/` holds the run's generated output as well as its code, so "allowed unless listed" defaults to editing the evidence the acceptance test measures. What the table cannot see at all is a patch that leaves `package.json` untouched and quietly drops a suite from `scripts.test` — `package.json` is not a banned file — so `readTestChain` before and after the turn plus `testChainIsIntact` is the second check: removing a suite is a refusal, adding one is a warning.

    **An unjudged patch is live code, and that changes what the manager may do next.** `fix.js` works in `main`, not a branch (the branch idea was dropped 2026-10-05: one team at a time, and a patch may not land while a run is in progress — gotcha 66's rule that a carry-forward gate cannot tell a code change from a data loss). The patch stays uncommitted while the manager judges it, because the commit IS the acceptance act and only the dev team makes it. Which means a `proposed` patch is already in the tree, so act mode refuses the whole plan while `unresolvedPatches()` is non-empty: running a step now would produce a before/after measurement that cannot say whether the patch or the step moved it. Two consequences of that, both found while testing. The "the tree already holds changes no patch declares" refusal had to move **inside `workTicket`, after the tree is read and before `createPatch`** — a refusal that opened the patch first left a dangling `proposed` record gating act mode for a change nobody proposed. And `--verify` only **warns** about undeclared changes, because it mutates nothing; refusing there would make the read-only command stricter than the mutating one. Related: a refused proposal attempt is **history, not current state** (`refusedAttempts`, with `problems` cleared when a later attempt lands — otherwise the report describes a patch that no longer has that problem); judging a patch is not a ledger entry (the patch record is the record, and the ledger records the consequence, which is the wipe-and-cascade); and a judgment reason is checked, not just required — "I accepted it because volume 15 passes now" is refused, because that is the complaint stopping, not the change being sound (gotcha 70 again).

    **Git has to be asked, not guessed, and this repository is the reason.** `ai-client/` is its own git repository (split out of the parent `oresuki/` folder on 2026-10-06, which now ignores it), and the working tree of that parent holds ~800 deliberate changes belonging to the account owner's in-progress translation output. So every git call runs **inside** `ai-client/` and is path-scoped (`git status --porcelain -uall -- <relative root>`, `git add -- <the patch's declared files>`, `git commit -m … -- <files>`), and neither `git add -A` nor `git -C ..` is ever used: both commit somebody else's work. `-uall` is required because plain `--porcelain` collapses a brand-new folder into a single entry, and both the "extra changes" list and `revertPatch`'s `leftBehind` must name FILES — a folder name in a list a human is supposed to act on is not actionable. `gitRootOf` asks `git rev-parse --show-toplevel` instead of guessing from the folder layout, because a patch record written in a subfolder of a repository whose root is elsewhere is exactly the case where guessing produces a "clean tree" reading of a dirty one — and here the two roots are one folder apart.

    **The fixture half, because a dev-team test is a git test.** A fixture repo needs its own `git config user.email` / `user.name` / `commit.gpgsign false` (the identity has to be inherited by `commitPatch`'s own git calls), its patch records kept in a channel folder OUTSIDE the repo (otherwise the records are undeclared changes in the tree being fingerprinted), and its own `package.json` carrying BOTH pinned scripts — `npm` resolves the nearest `package.json` walking UP the tree, so a fixture without one runs the real project's test chain from a temp folder. And the fixture's `glossary.js` is the volume-15 bug on purpose (gotcha 68's whole-cell relevance match), because the first real job for this team is the two unfixed halves of that incident: `truncateGlossary` comparing the whole term cell instead of the aliases inside it, and the extraction prompt's unenforceable "do not re-add a term as new merely because it is absent from what you can see here".


76. **A loop that drives the pipeline has to call the commands, not the functions — and a menu entry with no command behind it is a report, not a menu.** `autopilot.js` is the last piece of the delivery layer, and four things it needed turned out to be missing pieces of the pieces.

    **A code fix takes effect at a process boundary, so the loop spawns commands.** The first shape of the loop was `while (action.type !== "end") { switch (action.type) { run | diagnose | fix } }` calling `delivery.runActPlan(...)` in-process. That is wrong for this codebase specifically: Node caches a module the first time it is required, `gulpfile.js` requires all ten task modules at the top of the file, and `delivery.js` is not a banned patch path — so a patch that changed `utils/prompt.js` or the gates themselves would have been invisible to a loop that had already required them, and the loop would have gone on executing the **pre-patch** gates for the rest of the run. That is gotcha 66's failure class wearing a new hat. Spawning the account owner's own command per action is the reload boundary, it is cheap here because the idempotent skip-checks make a re-run nearly free, and it has a second benefit: the loop cannot reach past a gate, because there is no gate to reach past — it can only type the command. Related, and settled the same way: the loop takes **no run lock of its own**. `delivery.js --mode=act` takes one under the newest recorded run, so a loop-wide lock would make its own children refuse; and holding a lock across the whole loop would claim "a run is in progress" during the `fix` branch, which is exactly the case gotcha 66 forbids (a patch may not land while a run is working on the volumes). What the loop does instead is check `runInProgress()` before each action and stop if something else started.

    **Three menu entries had no command behind them.** `DELIVERY_ACTIONS` listed `open-ticket`, and `planResume` proposed it, and nothing executed it: `executableSteps` returns `[]` for a plan whose resume point is a ticket, so act mode ran nothing and only a *gate refusal* ever reached `openTicketFor`. `recordChoice` was reachable only from code, so an answered ticket could be read but not acted on — which meant the dev team, summoned only by an option marked `requiresCodeChange`, could never be summoned at all. And there was no entry for choosing, judging a patch, or sending the dev team. The fixes are `delivery.js --open-ticket` and `delivery.js --choose=<optionId> --ticket=<id> --reason=<text>`, three new Tier A entries (`choose-option`, `dev-team-patch`, `judge-patch`, all `countsAsIntervention: false` because the counted consequence is the wipe-and-cascade that applies a patch), and `ACTION_MENU_ENTRIES` in `utils/manager.js` mapping every decision the manager may name to the entry that gives it a command — pinned by a test, because "the two menus are different lists on purpose" is exactly the situation where drift is invisible. Two details that are not details: `--open-ticket` writes the question from `questionForEscalation`, keyed on `plan.escalation`, rather than `openTicketFor`'s "has been tried and the deliverable did not move" — the triage **refused** to try, so the old wording would have stated an attempt that never happened, and a ticket whose "already tried" list is a fiction gets answered by switching the guard off (gotcha 70). And it is **idempotent**: a live ticket for that exact step/volume/finding is named rather than duplicated, so the loop may call it every iteration; two tickets for one complaint put the same question in front of the diagnostics team twice and make the ledger's account describe neither.

    **A triage that cannot read its own correspondence re-escalates the same shape forever.** `utils/resume.js` read the ledger but never the tickets or the patches, so the plan's `open-ticket` verdict was purely disk-shaped: after the dev team landed a fix, the next triage saw the same disk shape and escalated the same question again. So `readWorkingState` now attaches `tickets` / `patches` (kept on the state so `planResume` stays a **pure function of a snapshot** — a hand-built test state must not silently read the live series' history, which is gotcha 71's trap in a new form), and an accepted or committed patch answering a ticket **supersedes** the escalation: the plan becomes `run` / `wipe-and-cascade` with a reason naming both the ticket and the patch. The supersede is deliberately asymmetric, and the asymmetry is the lesson: it applies to the three "re-running reproduces the same result" checks and **not** to `intervention-budget`, because a code change cannot un-spend attempts this run already made, and applying the patch is itself the counted wipe-and-cascade. A test caught that one — routing the budget escalation through the same `escalate()` helper made it supersede-able, which would have refunded attempts the run had already spent.

    **The manager's decision has to be a call with no tools, and its answer has to be a shaped record.** Everything else in this layer is deterministic; the only thing that needs a model is "of the moves available to me, which one now?". Handing it an agent handle would hand it file-reading tools, and the whole "never sees the code" guarantee (docs/delivery-layer.md) would become a sentence in a prompt instead of a capability it does not have — the same two-layer lesson as gotcha 74 and gotcha 75, in the direction where the role is not allowed to read at all. So `managerDecision` is `harness.runOneShot` with no `tools`, one message in, one fenced JSON block out, `parseManagerAction` fail-closed, and `validateManagerAction` refusing anything the records do not support. Two consequences worth naming. `end` is proved, not believed: `endIsProvable` checks the triage's verdict, open tickets, unjudged patches, and the deliverable's `missing` / `unverified` counts, because "I think we are done" is the claim a loop would otherwise exit on. And an unattended **accept** is gated by `safeToAcceptAutomatically` rather than by the manager's judgment, because in an unattended loop *every* accept is unattended — ordinary project code, pinned checks green, no warning, nothing escalated in prose, no measured regression, or the loop stops and names the account owner. Rejecting needs no gate: it is the direction that undoes work. Both are followed by the command that finishes them, because accepting is not landing a change (`fix.js --commit`) and rejecting is not undoing one (`fix.js --revert`) — and a rejected-but-not-reverted patch sits in `unresolvedPatches()` and gates the next run.

    **Watch mode is the only safe rehearsal, and a preview has to say it is a preview.** Act mode refuses `--no-write` and refuses `--dry-run` passthrough because a recorded intervention that did nothing poisons the ledger that exists to catch a spin (gotcha 72). So the default mode records nothing at all — no ticket, no ledger entry, no plan file, no lock — and prints the decision, the whole menu, and the exact command act mode would have run (`commandFor` / `describeCommand` are one function so the two cannot drift). One wrinkle: with no ticket written, `diagnose` is an illegal move, so the manager's only legal answer at the volume-15 shape would be `escalate` — a correct reading of a state whose honest answer is a question. Watch mode therefore shows the question `--open-ticket` *would* write as a record whose status literally reads `PREVIEW — not written`, which makes the rehearsal mean what it claims while writing nothing. Related, and cheap to get wrong: `answer` must say **which** question it answers when a ticket has more than one open, because `recordAnswer` matches the team's wording exactly and `diagnose.js` refuses to guess — so the loop passes the ticket's own text, not the model's paraphrase, and the gate refuses a paraphrase that matches nothing instead of spawning a command it knows will exit 2.

    **On this machine a manager that answers nothing is a container problem, not a model problem.** Every local container advertises the same model id (`local`) on one shared port, so `harness.assertModelServing()` cannot tell them apart; the only record of which one the `pre-manager` hook started is `hooks/.model-switch-state`. A manager turn served by the translation container answers with nothing. So `managerDecision`'s failure message names that suspicion out loud rather than reporting "the model returned no content" and leaving a human to find it in `.logs/` (gotcha 22, gotcha 62) — and the hooks fire around the role's **own** turn (`runTurnWithHooks(MANAGER_TASK, …)` inside `utils/manager.js`, `utils/diagnostics.js`, `utils/devteam.js`), never around a CLI that merely *might* reach the model, because a switch costs a model load and a CLI cannot know without repeating every refusal the module makes.

77. **A staged book is a shortcut to the original, and the two ways a shortcut is invisible both
   had to be closed.** The intake step used to `copyFile` each book into the volume folder it named,
   which on the live series meant 203 MB of books cost 406 MB — the pipeline's single largest output
   was a duplicate of its own input. `stageSourceFile` (utils/fs.js) now links the book instead, and
   `stageVolume` plus the deterministic `--dry-run` layout both go through it. Three rules are
   load-bearing, and each one is a failure mode a shortcut introduces that a copy does not have:

   - **Nothing is ever written through a broken shortcut.** `readFile` and `copyFile` both FOLLOW a
     shortcut, so the ordinary "is something already staged there?" answer for a dangling one is
     "no" — and the ordinary "put the book there" call then creates the file at whatever the shortcut
     POINTS at, not in the volume folder. That is a write landing outside the folder the sandbox
     confined it to, which is the one property the intake gate exists to guarantee. So the destination
     is inspected with `lstat` (which does not follow) before anything is decided, a shortcut that
     resolves nowhere is a refusal naming what it points at, and the copy fallback removes the
     shortcut IT just made before copying — otherwise the fallback itself is the write-through.
   - **`Dirent.isFile()` answers NO for a shortcut, and three checks asked the cheap directory
     question.** `utils/postmortem.js`'s file listing (the "is this folder holding exactly what the
     pipeline writes?" check — gotcha 67), the deterministic layout's scan for loose books at the
     series root, and the intake step-cap's candidate count all used it. Left alone, every book the
     previous intake staged becomes invisible: the post-mortem could no longer see a stray shortcut
     in a volume folder, and a `--dry-run` would re-stage the whole series into a rival set of folders
     beside the committed ones — gotcha 31's exact failure in a new costume. They now ask for a file
     OR a shortcut that resolves to a file (`isSourceEntry` in get-translation-target.js, the
     stat-checked listing in postmortem.js). The direction matters both ways: a linked book is the
     volume's source, not a stray, and a stray shortcut is still a stray.
   - **The shortcut is RELATIVE, and that is gotcha 11 applied to the filesystem.** An absolute
     shortcut is a promise about this machine's paths; this project already migrated once, and a
     Windows `C:\...` path baked into the plan of record is not absolute on Linux. A relative link
     keeps working when the series folder moves, is renamed, or is checked out elsewhere.

   What the shortcut gives up, and what stands behind it: the volume folder no longer holds its own
   book if the one at the series root is deleted, so "the source file is missing" now has two shapes
   and `resolveSourceBundle` names which one it found (`shortcutTarget` reports where the name points
   and whether that file exists). `manifestSourcesExist` catches it at every task's entry, and the
   failure is structural — the same rule that stops a run from continuing past a missing book. The
   write gate needs no change: it refuses archives by NAME (`isArchivePath`), and a shortcut named
   `book.epub` is refused exactly as the book was. Where linking is impossible (a different drive, a
   filesystem with no links, a Windows checkout without the privilege) staging falls back to a copy
   and the answer says which one happened, so the intake step cannot be killed by a filesystem
   detail. `test/test-intake.js` pins the link, the broken-shortcut refusal (including "nothing was
   created at the path it pointed at"), and the linked-book dry-run preview; `test/test-postmortem.js`
   pins both halves of the listing rule; `test/test-pipeline-loop.js` runs the whole ten-step pipeline
   on linked sources and still makes zero calls on its second pass, which is what proves the source
   fingerprint read through a shortcut is stable.

78. **A step cap cannot tell "still working" from "spinning", so the delivery layer's turns are uncapped — and the
   thing that makes that safe is putting the reading on DISK, not a bigger number of steps.** The diagnosis turn that
   forced this change (`diagnose-TCK-delivery-2026-10-06T18-27-38-632Z-1`) ran 702 seconds and **7,217,748 prompt
   tokens** across 73 tool calls, re-opened `glossary.js` twelve times, hit its cap at step 39, and answered with
   **zero characters**. Its last request was ~360,000 tokens against a 262,144-token window. The answer it never gave
   was already written in this file, in gotcha 68. Three separate defects were behind it, and only one of them is a
   step count:

   - **The window was only checked at the START of a turn.** The library compacts a session when a turn begins, not
     while one is running, so a turn that grew past the window mid-work never saw a compaction — it just kept paying,
     and the server eventually refused the request. A 700-second turn is a sequence of dozens of requests, and only
     the first one was measured.
   - **The library estimates tokens as `JSON.stringify().length / 4`.** This project measures Japanese at 1.6–1.7
     characters per token (`utils/tokens.js`, gotcha 54). A library estimate is not a measurement, and the pipeline
     already had a calibrated one that the harness was not using.
   - **Pipeline-stage agents had silent lossy compaction switched on by default** (the library turns it on whenever a
     context window is configured, which is every handle in this project). That is gotcha 56's failure — the artifact
     gets worse and nothing reports it — happening in stages nobody had agreed to compact.

   What the fix is, and the four rules that hold it up:

   - **Compaction is off on every handle** (`autoCompact: false` in `createAgentHandle`). With it off, a request that
     genuinely does not fit comes back as the server's own refusal, which `tagSizeOverflowError` tags as
     `tooBigForOnePassError` and `runVolumeWithModeFallback` repairs by re-running the volume chapter by chapter.
     **A stage that used to compact quietly now fails loudly and recovers** — that change in behaviour is the point,
     not a regression, and it is the direction gotcha 55 was already built for.
   - **The delivery layer is uncapped, and it offloads.** `agent.maxSteps` becomes the size of a CHUNK instead of the
     size of a turn; between chunks the harness moves the turn's old read answers to
     `<run dir>/agent-<name>/turn-NNN-memory/` and continues the same conversation. The conversation keeps one map
     block per offload (every file the turn looked at, and how to get the text back) plus a one-line pointer where each
     moved answer used to be, so the agent never loses the fact that it saw something. `recall_memory` reads it back
     verbatim. Nothing is discarded.
   - **The pressure line is the load-bearing piece, not the tools.** The paper this design came from
     (arXiv:2607.23809) measured a model calling offload/recall tools about **zero** times unless it was told to. So
     every tool answer carries a line saying how full the working window is and what to do about it BEFORE the next
     read. A memory tool the agent is never prompted to reach for is a memory tool that does not exist.
   - **Compaction is limited to the delivery layer, deliberately.** A pipeline stage agent's job is to hold the
     artifact it is amending and the text it is amending in front of it at the same time; handing it `manage_context`
     would let it set aside the text it is required to preserve — gotcha 64's 457 vanished glossary terms, rebuilt out
     of good intentions. `CONTEXT_MANAGED_ROLES` is the opt-in list, a non-managed handle runs exactly ONE chunk (so
     every stage keeps its own scaled cap and its own step-cap warning unchanged), and `prompt-audit.js`'s
     `stage-context-offload` rule fails the offline pipeline if a stage request ever advertises either memory tool.

   What to keep in mind when working with this:

   - **The wall on an uncapped turn is repetition plus a loose clock, not a step count or a spending limit.** The
     repetition detector counts a call as a repeat only when the tool, the arguments AND the answer are identical, and
     it watches the RAW answer before the pressure line is appended — otherwise every call would look like a repeat of
     itself. Consequence worth knowing: with `AGENT_REPEAT_LIMIT=3`, three identical refused writes in one dev turn
     abort that turn mid-work. And there is deliberately no token budget here, for gotcha 69's reason: a spending
     limit hides the spin behind a cost error, and the spin is the thing this layer exists to catch.
   - **When nothing can be moved, say so.** An offload that finds nothing eligible stops the turn with "this does not
     fit in one turn" rather than falling back to a summary of the conversation. The honest failure is the one the
     account owner can act on; a summary is how the artifact gets worse with no error to notice (gotcha 56 again).
   - **The record of such a turn is its shape, not its limit.** `turnShapeOf(result)` (utils/agents.js) stores
     `{chunks, toolCalls, offloads, offloadedTokens, compactions, endedAs}` on the diagnosis record and the patch
     record, and `fix.js` prints it. `endedAs` keeps the harness's own word for the ending verbatim, so a record can
     never soften "stopped" into "finished", and `compactions` is counted because a turn that compacted is a turn that
     lost something. A turn that threw before the harness handed a result back records `turnShape: null`, not a shape
     of zeros.
   - **The number in the pressure line is the honest half available.** Tools run before the model reports its usage,
     so a tool answer's line is built from the PREVIOUS request's count plus this project's own calibrated estimate of
     the whole conversation, whichever is larger. In production the server's own count is the accurate half; in a
     test, a scripted reply that reports `estimateMessagesTokens(req.messages)` keeps it honest.

   `test/test-context.js` pins the module (what may move, what may never move, the eligibility floor that stops a moved
   answer from being moved again, the recall budget in BYTES, both detectors, the turn clock, `turnShapeOf`, and that a
   misspelled `requestOffload` fails the handle instead of answering the agent's one request for help with a tool error
   — the real bug the live probe found). `test/test-fake-backend.js` runs the whole thing through the real agent loop:
   three chunks, two offloads (one at the hard limit, one the agent asked for), `compactions: 0`, the map blocks and
   pointers visible on the wire, a stuck agent stopped for repeating itself, and a stage handle whose oversized pass is
   tagged as the size failure the fallback repairs. `test/test-diagnostics.js` and `test/test-devteam.js` each assert
   the old cap names are ABSENT from their role module. See docs/delivery-layer.md "Uncapped turns".

82. **A relevance test that compares whole glossary cells is a furigana-blind test — and a window that hides entries has to stop hiding them at the level of names.** The producer side of the volume-15 chain (gotcha 68): the gate was fixed first, and the reason the gate kept being handed a rename to interpret was `truncateGlossary`.
    - **What the old rule could not see.** It kept a row when `sourceText.includes(wholeFirstCell)`. Measured on the live pair — volume 14's 445-row glossary against volume 15's eight chapters — the whole-cell rule found 45 of the 445 carried rows relevant to the volume (5–23 per chapter); reading the spellings inside each row finds 70 (7–35 per chapter). The row that started the chain was invisible in chapter 6, so the extractor re-proposed its term as brand new.
    - **Why comparing whole strings cannot work in this corpus.** A glossary writes a term the way the glossary writes it and the book prints it the way the book prints it: `双ふた花ばの恋物語` against `双ふた花ばの恋こい物もの語がたり` — furigana inserted INSIDE the word, so neither string contains the other and every whole-spelling test says "this term is not in the text" about a term the text prints. The form in which the two ARE the same string is the term's Han characters in order with every kana dropped, which is what a term looks like once you stop writing its furigana: both spellings have the skeleton `双花恋物語`. So a row counts when either (a) any spelling its term column names occurs verbatim, or (b) that skeleton, **at least `GLOSSARY_SKELETON_MIN_CHARS` (3) long**, occurs in the same projection of the source. The minimum is not decoration: 学校's skeleton is two kanji, and two common kanji sitting next to each other happen all over a real page, so a shorter skeleton matches everything and therefore proves nothing — the same reasoning as `CARRY_FORWARD_MIN_ALIAS_SPAN_CHARS` in gotcha 68.
    - **Deliberately loose on the false-positive side, and the asymmetry is the reason.** A row shown to the extractor that the chapter happens not to mention costs a few hundred characters of prompt. A row hidden from it costs a re-proposed term, an amend reconcile, and a gate that has to tell a rename from a deletion. Buy the cheap mistake.
    - **One definition of "the spellings inside a row".** `glossaryTermSkeleton` lives in `glossary/carry-forward/table.js` beside `glossaryTermSpans`, and `glossary/extract.js` imports it rather than writing its own matcher. Two definitions of what a row names is exactly how the extractor and the gate end up disagreeing about the same row, which is gotcha 68 in one line.
    - **The window now hides a row's Notes, never an entry.** `GLOSSARY_TRUNCATION_MAX_ENTRIES` (200) bounds how many rows are shown *with their Notes*; the excerpt ends with `buildGlossaryIndex`'s complete name-and-rendering list of the whole file — 445 terms for 14.7 KB, against the ~55 KB those 200 rows cost. That is what makes the note's "a term named there is NOT new" checkable at all: the extractor is a one-shot call with **no file tools**, so a warning telling it to go and look at the glossary file is a warning it cannot obey. Verified against the live pair: the term that ended the run is named in all eight chapter windows, and the largest extraction prompt (chapter + window) is ~48k estimated tokens against `AI_CONTEXT_WINDOW=262144`.
    - **And the row count became honest.** A stray `|` line survives in a real glossary, and `collectDataRows` counted it as an entry: the note announced "446 term rows" for a 445-row file, and a junk line competed for a slot in the window. A row with nothing in its first column is not an entry.
