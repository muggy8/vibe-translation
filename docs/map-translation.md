# The file map — the translation stage

The five translation tasks and the helpers they share.

Part of the ai-client documentation; the entry point is [AGENTS.md](../AGENTS.md).

## The file map — the translation stage
| Path | Role |
|---|---|
| `utils/translation-report.js` | The series-level publish gate and its report (deterministic, no AI). `checkTranslationPreconditions` is the `translate` entry gate (a FAIL `consistency-report.md`, a stale/missing audit, or a volume with no `glossary.md` stops the stage before a token is spent — `--allow-fail` / `--allow-no-glossary` override). `writeTranslationReport` reads every volume's `translation-state.json` + `translation-verification.json` + `polish-verification.json` and writes `translation-report.md` (+ `.json` + provenance sidecar) at the series root: per-chapter outcome (PUBLISHED verified / UNVERIFIED / MISSING / EMPTY IN SOURCE), verify score, retranslate attempts, ratchet state, polish verdict, and the volume-level rendering-variant counts. Called at the end of `translate`, `translate-qa` and `polish`, and available as its own gulp task. **It is also the only reader of its own output**: `readTranslationReport(seriesDir)` reads the machine-readable sidecar back (null when absent or unparseable — a roll-up that cannot be read is absent, not empty) and `summarizeReportRows(rows)` is the one roll-up of the outcome buckets, the median score, the two deterministic drift counts and the published character count. `utils/resume.js` and `utils/delivery-verify.js` both read through these, so the publish report cannot be counted two different ways by two consumers (see gotcha 73). |
| `translate.js` | Translation task (first stage of the multi-model chain; docs/pipelines.md §8.5). Per volume, per chapter (in `bundle.segments` order): skip when the draft + `translation-state.json` cover the current source/reference hashes, size each chapter's parts with `planChapterSplit` (tokens — see docs/architecture.md "Processing mode" and gotcha 57; `TRANSLATE_CHUNK_CHARS` is a ceiling only when explicitly set), translate each part via `runOneShot` on the `TRANSLATE_*` endpoint — **no system prompt** (Index-Translate's single-user-message instTrans contract), the model's own greedy decoding, fast non-thinking mode by default (`chat_template_kwargs {enable_thinking: false}`) — with the previous part's ending as continuity context, deterministic QA (`checkTranslationQa`), per-chapter state persistence, and the merged `translation.md` + `translation-qa.md`. **Entry gate:** `checkTranslationPreconditions` refuses to start the stage on a FAIL (or missing, or stale) `consistency-report.md`, or on a volume with no `glossary.md` — `--allow-fail` / `--allow-no-glossary` override. **A chapter that is empty IN THE SOURCE is skipped without a model call** (under `TRANSLATION_EMPTY_SOURCE_CHARS`, default 40) and recorded as "empty in source — not translated"; a segment the extraction flagged `empty` but that still has text is translated with a loud warning (a damaged chapter, not a missing one). **A deterministic-QA failure no longer discards the draft:** the bad draft is kept, the rejected attempt is quarantined to `translation-<id>.rejected.md`, and the state records `qaFailed` + `qaFindings` so `verify` can seed the verdict with NO model call and `retranslate` can repair it. **Completeness is checked at the END of the task** (a volume with chapters that have no text is a structural error, but chapters missing *because they are empty in the source* are a reported warning — one hole in volume 2 no longer stops volumes 3–17). Also exports `chapterArtifactNames` / `mergeVolumeTranslationFiles` shared by the other three tasks; `mergeVolumeTranslationFiles` returns `{text, missing, unverified}` and injects the UNVERIFIED marker (see docs/pipelines.md §8.5). |
| `verify-translate.js` | Verification task (docs/pipelines.md §8.5). Per chapter with a draft: one-shot source-anchored check on the `VERIFY_*` endpoint → 0–100 score (fail-closed: unparseable = FAIL) + severity-banded findings → `translation-verification.json` sidecar + `translation-verification.md` report. PASS = score ≥ `PASSING_SCORE` (default 70). **Borderline tiebreak (batched, cross-model):** after the verify pass, every chapter whose score lands within `±VERIFY_TIEBREAK_BAND` (default 5) of the passing score is re-scored on the `AUDIT_*` endpoint (a SECOND endpoint — the `verify-audit` hook switches its container in) and the two scores are **averaged** (one endpoint switch for the whole batch, never interleaved with the verify loop; an unparseable audit score keeps the verifier's score — fail-open). **Repeat sampling:** a chapter whose score lands within `±VERIFY_SAMPLE_BAND` (default 8) of the passing line is graded up to `VERIFY_SAMPLES` (default 2, max 5) times and the MEDIAN is used — one grader's bad hour is not a FAIL. **Deterministic seed:** a chapter the translate task already failed on the no-AI QA checks gets its verdict from that record (no model call) so the loop can repair it. **Rendering-variant scan** (`findRenderingVariants`, no model call at all): every glossary term used in the volume is checked against the PUBLISHED text for near-variants of its canonical rendering — a second rendering of the same source term (HIGH), different spacing/hyphenation (MEDIUM), different capitalisation or a plural alongside the singular (LOW). The per-chapter verifier reads one chapter at a time and cannot see this class at all; across the volume it is free. Findings go in `translation-verification.md` + the sidecar's `volume.renderingVariants`. **Cross-chapter consistency pass** (`runVolumeConsistencyPass`, default-ON, `VOLUME_CONSISTENCY_ENABLED`): the same audit batch also reads a volume's PUBLISHED chapters TOGETHER — the one thing a per-chapter check structurally cannot see (a name rendered two ways inside the volume, a fact chapter 3 states and chapter 9 denies, a tense/POV shift, a contradiction with the previous volume's ending). One call per audit WINDOW (a volume larger than the auditor's context is split into consecutive windows, each carrying the previous window's tail, and the report says which chapters were never compared); findings are chapter-tagged (`FINDING [HIGH] chapters=ch3,ch9 — …` with both sides quoted) into `volume-consistency.json` + `volume-consistency.md`, and a HIGH finding makes even a 92-scoring chapter a retranslate target. **Glossary disputes:** a verifier reply may raise a `GLOSSARY DISPUTE:` block (the translation was right, the glossary was not); those are recorded per chapter and aggregated into the series-root disputes queue at the end of the run. `VERIFY_TRANSLATE_ENABLED=false` makes it a no-op. Exports `loadVerificationSidecar` (read by retranslate), `glossaryBlock` + `findingsOf` (read by polish); returns the aggregated run summary (`failed` — read by the `translate-qa` loop). |
| `retranslate.js` | Correction task (docs/pipelines.md §8.5). Per chapter that FAILED verification (and whose sidecar entry still covers the current source + draft): a fresh pass on the `TRANSLATE_*` endpoint with the verification findings injected as a numbered `【硬性要求】` "fix these" constraint in the instTrans prompt — the bad draft is **deliberately not** fed back (re-reading a bad translation anchors the model to its errors). Same part-by-part splitting as `translate` — the SAME `planChapterSplit` call, so the two tasks cannot cut one chapter differently (a retranslate would otherwise produce a differently-shaped chapter than the one verify graded) — and the findings are injected into every part. Overwrites the draft, updates the state (invalidating any earlier polish), re-merges `translation.md`. **Value filter** (`worthRetranslating`): a chapter that missed the passing line by less than `TRANSLATE_RETRANSLATE_VALUE_MARGIN` (default 5) on MEDIUM/LOW findings only is a copy-edit, not a re-translation — a fresh pass can introduce new errors while fixing a nit and costs a whole chapter of generation. A HIGH finding, a deterministic-QA failure, or an unparseable score is always worth it; skipped chapters are COUNTED and reported, never silently dropped. **Targeted correction** (`TRANSLATE_TARGETED_FIX`, default-ON): when the findings quote spans that can be located in the source, only those passages are re-translated and the corrected text is stitched back into the draft (`planTargetedRepair` → `runTargetedRepair` → `stitchParagraphs`) — one bad sentence no longer costs a whole chapter of generation and a fresh chance to break what was already right. The shortcut is REFUSED (and the whole-chapter pass runs) whenever the source↔draft mapping is not trustworthy: paragraph counts disagree, a quote cannot be found, the affected span covers the chapter, or an affected draft paragraph is not a plausible rendering of its source span. The stitched chapter is re-checked by the deterministic QA; a failure is quarantined to `translation-<id>.rejected-passage.md` and the whole-chapter pass runs. Each passage pass sees only its own findings (a finding about paragraph 7 is not injected into the pass rewriting paragraph 2), plus the surrounding translated text as the seam it must match. **Cross-chapter repair:** a chapter that PASSED its own verification but is named by a HIGH `volume-consistency.json` finding is repaired too, with those findings injected (the value filter never applies to a contradiction). The ratchet baseline (`bestScore` / `bestDraftHash` / `bestVerdict`) SURVIVES a retranslate — that is what lets the loop roll a worse rewrite back. Runs only when verification is enabled; returns the aggregated run summary (`retranslated` — the `translate-qa` loop's stall guard). |
| `translate-qa.js` | The batched translation QA loop (docs/pipelines.md §8.5) — one gulp task that mirrors the pre-production “translate → validate → apply → re-validate …” loop: up to `TRANSLATE_QA_MAX_ROUNDS` rounds of [verify batch (`VERIFY_*`) → retranslate batch (`TRANSLATE_*`)], stopping when every chapter passes, a round retranslates nothing (stalled), or the round cap is hit. Batched because the local model containers share one port: each half-round is a whole single-endpoint task run invoked through `withHooks()` (the per-batch model-switch hooks fire at every boundary). Owns no prompt/model logic — the stop-decision is the pure `qaLoopDecision` in `utils/translate.js`, and `reportVerifyStop` is only the sentence that tells a human what to do next. |
| `polish.js` | Final pass (docs/pipelines.md §8.5). **Two-phase, batched, cross-model.** Phase A (per chapter, the `EDIT_*` endpoint, thinking on): one-shot polish — **the polisher sees NO source text** (surface cleanup of already-verified text) → deterministic regression guard; a guard-gated candidate is written and queued. Phase B (batched, cross-model): the **final audit** on the `AUDIT_*` endpoint (a SECOND endpoint, distinct from the polisher's — the `polish-audit` hook switches its container in; the whole batch runs under one endpoint, never interleaved with the polisher) scores each candidate on the source-aware drift rubric (0–100, PASS ≥ `PASSING_SCORE`, fail-closed). A FAIL re-polishes on the `EDIT_*` endpoint (the `polish` hook switches back) with the findings injected as a numbered "fix these" task (the retranslate pattern) and is re-audited next round; up to `POLISH_QA_MAX_ROUNDS` (default 3) rounds, on exhaustion the draft is kept (any polished file is dropped so the merge publishes it) and the findings persist (the next run re-audits with them; `--force` = a fresh attempt). Runs on whatever drafts exist (including round-cap FAILs). Writes `polished-<id>.md` + `polish-verification.json`, records `polishedDraftHash` + `polishVerifiedDraftHash` (set only when Phase B accepts) in the state, re-merges `translation.md` (polished text wins). Its commit phase (`finishPolishVolume`) drops the candidates that never passed the audit, re-merges, and SAVES the state (the cleared polish hashes + the kept findings — the promise that the next run re-audits with them is this save, not some earlier phase's). |
| `utils/translate.js` | Pure translation-stage helpers shared by the four tasks: `splitChapter`, **`planChapterSplit` (the chapter-part size rule, in tokens: the ADMISSION limit — `part + references + findings + instructions + 52 + max_tokens <= safetyFraction × window` — and the FEASIBILITY limit — `part × outputRatio × thinkingFactor <= max_tokens` — with the binding one reported and the character limit derived from the chapter's own measured characters-per-token; see docs/architecture.md "Processing mode" and gotcha 57), `translateChunkCap` (`TRANSLATE_CHUNK_CHARS` as a ceiling ONLY when it was explicitly set — `null` means the token plan decides), `outputRatioFor` (the per-pair expected output-token ratio, `TRANSLATION_OUTPUT_RATIO` override; a TOKEN ratio, not the CHARACTER band in `lengthBands`), `thinkingOutputFactor` (reasoning is billed as output: `no_think` 1× / `low` 2× / `high` 3×) and `measureOutputRatio` (the ratio this series' already-translated chapters actually produced, read off disk and clamped so one lucky volume cannot loosen the plan)**, `parseGlossaryTerms`, `extractStyleRules`, `buildTranslationTaskLines` / `buildTranslationPrompt` / `buildBudgetedTaskLines` (the Index-Translate instTrans shape: a header naming source language, genre and target language, a `【源文】` block, a numbered `【约束要求】` list whose `【硬性要求】` lines are binary constraints and whose `【注意】` lines are graded ones, and the output-only suffix; `languageName` maps the pipeline's English language names to the trained Chinese ones and `translateGenre` is the header's genre slot), `cjkRatio`, `countOccurrences` (substring for CJK, `wordBoundary` for space-separated sources), `residueRatio` (per-pair source-script residue: the source script minus the target script — JA→EN counts kana+Han, JA→ZH only kana, KO→EN Hangul, ZH→EN Han), `isSpaceSeparated`, `lengthBands` (per-pair length band, `TRANSLATION_LENGTH_RATIO` override), `scriptsOf`, `checkTranslationQa` (hard fails: empty draft, source-script residue > 5%, length under the pair's truncation floor; warnings: residue > 0.5%, length outside the pair's band, missing glossary renderings), `buildPolishGuardFindings` (the polish loop's correction tasks synthesized from a failed guard check), `mergeVolumeTranslation`, `stripMarkdownFence`, `stripThinkBlock` (drops a leading `<think>…</think>` a reply may carry even though the stage asks for the fast mode — the think tag is this template's default, so the backstop is not optional), `tailOf`, `stripContinuityOverlap` (strips the previous part's ending if the model repeats it at the start of its reply — the deterministic dedup backstop for the continuity tail), `runWithConcurrency` (bounded worker pool for the per-chapter loops), `stageConcurrency` (the shared `STAGE_CONCURRENCY` knob, default 1; legacy `<PREFIX>_CONCURRENCY` per-stage overrides still honored), `judgeTemperature` (`JUDGE_TEMPERATURE`, the grading temperature), `stageThinking` (`AI_THINKING` + `STAGE_THINKING_LEVEL`, the stage calls' thinking dialect), `writerTemperature` (a writing stage follows `AI_TEMPERATURE`), `loadTranslationState` / `saveTranslationState` (fail-open), `roleEndpoint` (`<PREFIX>_BASE_URL`/`_API_KEY`/`_MODEL` with `AI_*` fallback; also reports `modelSource`/`baseUrlSource` for logging), `loadVolumeReferences` (glossary terms, style rules, wiki + POV-map background, voice notes, and the `contextHash` idempotency key — the references are injected BY RELEVANCE to the volume being translated, see docs/pipelines.md §8.5), `qaLoopDecision` (the translate-qa loop's pure stop-decision: all-pass / round-limit / stalled / missing-drafts / no-improvement) and `qaMaxRounds` (the `TRANSLATE_QA_MAX_ROUNDS` cap). **This module is also the shared artifact layer** (it used to live in `translate.js`, which made `translate.js` ↔ `verify-translate.js` a require cycle): the artifact-name constants (`STATE_FILE`, `QA_REPORT_FILE`, `MERGED_FILE`, `VERIFICATION_FILE`, `VERIFICATION_REPORT`, `POLISH_QA_REPORT`, `POLISH_VERIFICATION_FILE`), `chapterArtifactNames` (+ `bestFile` = the ratchet's restore point, `rejectedFile` = the quarantined QA failure), `readFileOrEmpty`, and the sidecar I/O (`loadVerificationSidecar` / `saveVerificationSidecar`, `findingsOf`, `glossaryBlock`) — `translate.js` and `verify-translate.js` re-export them for compatibility. Plus: `medianScore` + `verdictCoversCurrentDraft` + `unverifiedMarker` (the publish gate's marker text), `recordBestDraft` / `applyDraftRatchet` (the draft ratchet, docs/pipelines.md §8.5), `worthRetranslating` (the retranslation value filter), `previousVolumeTail` (cross-volume continuity: volume N+1's first chapter sees the tail of volume N's PUBLISHED text), `findRenderingVariants` / `renderVariantFindings` (the deterministic drift scan), `estimateTokens` (re-exported from `utils/tokens.js` — the estimate now lives there, calibrated per model) / `fitPromptBudget` (bills the chat wrapper ONCE, the same rule `tokenBudgetFor` uses, and reports the charge as `templateOverhead`) / `describeDroppedBlocks` / `buildBudgetedTaskLines` (the prompt budget — see docs/pipelines.md §8.5) and `calibrateStageTokens` (stage-start: point the estimate at THIS role's model, so the translator's coefficients are not used to budget the auditor's prompt), `previousRunThroughput` / `logRunEstimate` / `progressCounter` / `countStageChapters` (the run estimate + heartbeats), `checkChapterListConsistency` (the handoff's `chapters.json` vs the extracted list), `headingForSegment` (the merge's heading rule, docs/pipelines.md §8.5), `EMPTY_SOURCE_CHARS`, `chapterContextHash` (per-chapter invalidation — its key includes the glossary rows the chapter actually uses AND whether each is disputed), `REFERENCE_SELECTION_VERSION` (baked into `contextHash` so a change to the injection rule invalidates the drafts built under the old one), `roleEndpoint` (+ `describeEndpoint`, and per-role `<PREFIX>_CONTEXT_WINDOW` / `<PREFIX>_MAX_TOKENS`). And the two cross-chapter layers: `resolvePublishedChapterTexts` (ONE rule for "what this volume publishes", shared by the merge, the variant scan and the cross-chapter audit, so the reports and the book cannot describe different texts), `planConsistencyWindows` / `parseVolumeFindings` / `findingsForChapter` / `volumeFindingsText` / `retranslateTarget` / `buildVolumeConsistencyMarkdown` / `loadVolumeConsistency` / `saveVolumeConsistency` (+ `VOLUME_CONSISTENCY_FILE` / `VOLUME_CONSISTENCY_REPORT`), and the targeted-correction helpers `paragraphBlocks` / `parseFindingItems` / `locateQuoteRange` / `planTargetedRepair` / `stitchParagraphs` / `buildPassageScopeLine`. |

## The implementation folders

Each of these modules is a thin public face (`x.js`) that re-exports a folder of cohesive
modules (`x/`). Node resolves `x.js` before `x/`, so every `require("./x")`, every test, and
every test that monkey-patches the harness keeps working unchanged — but the logic lives in
the folder, so open the module that owns the behaviour you are changing instead of reading
the whole layer.
