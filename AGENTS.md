# AGENTS.md — ai-client

**This file is the index.** The map, the architecture, the environment reference and the
hard-won gotchas live in `docs/`, one topic per file. Read the table in §2 before you open
anything, and read the gotchas that touch the area you are changing — they are the reason
most of this code looks the way it does.

## 1. What this is

An agentic AI client (v2.0.0, CommonJS, Node ≥ 22.19) that processes a light-novel series
**volume by volume** and produces translation-support artifacts — a glossary, a character
voice reference, a style guide, a wiki, a consistency audit — and then the translation
itself, chapter by chapter, through a multi-model chain (translate → verify → retranslate →
polish). It talks to any **OpenAI-compatible endpoint** through the Vercel AI SDK +
`@openharness/core`; tool-calling agents read the sources and write the outputs themselves
through sandboxed file tools.

On top of that sits a **delivery layer**: a deterministic step runner that assesses every
step, a run ledger that remembers what a run already tried, a ticket channel, a read-only
diagnostics role, a code-changing dev team, a delivery manager and a loop that drives them
(`index.js`, `delivery.js`, `diagnose.js`, `fix.js`, `autopilot.js`). See
`docs/delivery-layer.md`.

**Everything the pipeline writes — the deliverable and the run's own memory — lands in the
series folder**, not in this repo. The artifacts sit in the volume folders; the run's records
(its step reports, the ledger, the tickets, the patch records, the transcripts, the run lock)
sit in `<SERIES_LOCATION>/.run/`, which writes its own ignore rule so the records can be
committed with the books while the transcripts and the lock stay out. Change `SERIES_LOCATION`
and the next run gets its own memory instead of inheriting another series'. →
`configs/run-state.js`, `docs/environment.md`, gotcha 94.

### Quickstart

The books go in **`epub_source/`** (that folder *is* the default `SERIES_LOCATION` — unset
it and the pipeline looks there); the settings go in **`.env`** (`cp .env.example .env`).
`README.md` is the front door for someone who has never seen the project; this file is the
index for working on it.

| Command | What it does |
|---|---|
| `docker compose up --build` | **The whole pipeline in a container**: your books in `epub_source/`, your settings in `.env`, nothing else to install. `docs/docker.md` |
| `npx gulp discover` | Series intake only: work out the volumes, order, names, exclusions; write `translation-target.json` + `translation-plan.md` |
| `npx gulp glossary` / `character-voice` / `style-guide` / `jump-in-wiki` | One pre-production task (all volumes) |
| `npx gulp consistency-audit` | The cross-artifact sign-off (writes `consistency-report.md`) |
| `npx gulp translate` / `translate-qa` / `polish` | The translation stage (`--allow-fail` / `--allow-no-glossary` override the entry gate) |
| `npx gulp` (default) | All nine in order |
| `npm start` | **The front door**: the manager driving the whole run (`node autopilot.js --mode=act`). It starts the pipeline through `delivery.js --mode=act`, and when a step fails it opens a ticket, gets a diagnosis, and retries. The rehearsal — decide and print, execute nothing — is `npm run autopilot` |
| `npm run pipeline` | **The pipeline one step at a time** (`node index.js`): each step in its own process, each assessed, each recorded. `--stages=a,b`, `--post-mortem=off`, `--ledger=off`, `--fail-on=high\|medium\|never`, `--list` |
| `npm run delivery` | **Where the run stopped, and what to do about it.** `--mode=report` (default) proposes nothing; `--mode=act` executes the plan through the gated step runner; `--mode=act --stop-run` ends a run that is alive but has stopped making progress, which is the only move that touches a process |
| `npm run diagnose -- --ticket=<id>` | Answer a ticket with a **read-only** agent (it may open the code and the logs; it may not write) |
| `npm run fix -- --ticket=<id>` | Answer a ticket with a **code change**, inside a boundary; the machine runs the pinned checks |
| `npm run autopilot` | The manager driving the loop. Default `--mode=watch`: decide, print, write nothing |
| `npm test` | Offline tests (no AI, no network) — pure functions **plus** whole-task runs against the scripted model server in `test/fake-backend.js` |
| `npm run pipeline-loop` | **The whole pipeline offline** on a two-volume fixture, then a second pass that must make zero calls, then a 22-rule audit of what the pipeline actually asked the model |
| `npm run pipeline-loop-store` | **The same offline loop with the reference store switched on**, over a fixture cut into chapter-sized parts (`--stages=discover,glossary,character-voice --chunked=glossary --store-validators`). It is the only place the store path runs end to end offline, and the only place the glossary's chapter-by-chapter store path is reached. It is also the loop that caught gotcha 120. It used to be `pipeline-loop-chunked` and to force the character-voice stage chapter-by-chapter on its author route; that route is gone, so the loop is named for what is actually unique about it |
| `npx gulp character-voice` | **The character-voice stage. One route, no selector.** It reads the volume chapter by chapter, files what it found in the volume's record, and **renders** `character-voice.md` and `pov-map.md` from that record — no author agent, no feedback round, one acceptance grade, no agent turn anywhere in the stage. **`--route=` is refused for every value**, with a message naming what replaced the route: the author route (an author agent compiling the reference and rewriting it on feedback, with the whole-installment / chapter-by-chapter mode decision and `--chunked` belonging to it) was removed, not hidden, and it is in git history at commit `75e59a7`. `--chunked` is accepted and announced as a no-op — this stage reads chapter by chapter whatever the volume's size. The acceptance gate is the one both routes shared: same rubric, same three files handed to the grader, same quarantine-on-failure, same draft-record consequence. → `docs/map-preproduction.md` §6, gotcha 109 |
| `npm run extract-voice -- --volume=NN` | **Read one volume chapter by chapter and write its extraction notebook, and nothing else** — the manual door onto the same reading pass the stage's default route uses (`character-voice/reading.js`), for when a person wants to read a volume, or one chapter, without building the volume around it. One call per chapter; a chapter already read for the same text is not paid for twice; **a chapter whose answer never reached its closing bracket is named and re-read once at a lower reasoning level**, and a chapter still cut off after both paid reads is kept and printed as INCOMPLETE in the log, in `character-voice-reading.md`, and in the report the grader reads. `--chapter=<id>` re-reads exactly one chapter and reuses the rest for free — **and the answer it brings back replaces whatever that chapter's partial held, even when the old one held more claims** (measured on the real volume 02: ch1 111 → 51, ch5 78 → 53 — gotcha 122). It never writes `character-voice.md` or `pov-map.md`, seals nothing, and refuses a volume whose record is already sealed. → `docs/map-core.md`, gotcha 106, gotcha 111, gotcha 122 |
| `npm run rebuild-voice -- --volume=NN` | **Rebuild one volume's character-voice reference from the extraction output it already produced** — no model call anywhere, and not part of a run. Rehearses on a copy under `--out` by default; `--apply --move-aside` is what replaces the volume's file, keeping the old one as `.rejected`, and it publishes `pov-map.md` **with** it, before the seal. **A rehearsal of a volume that has volumes before it renders only that volume's own claims** — the published file also carries every earlier volume's sealed record in (measured on volume 02: 12 sections rehearsed, 15 published) → gotcha 108. `--render-only` is the door that renders **only** `pov-map.md` from the record a volume already has: it files no row, seals nothing, and works on a sealed volume because publishing a map the record's own published claims describe edits no row (gotcha 109). → `docs/map-core.md`, gotcha 98 |
| `npm run reopen -- --volume=NN --reason="…"` | **Reopen one volume’s published reference record as a recorded act** — the door that exists because “this volume’s record is untrustworthy and every chapter must be re-read” used to have no legal answer. The act is **retire and re-derive, never unseal**: a row is written into `record_reopens` with the reason, `series.db` moves whole to `series.db.retired-<stamp>`, the volume’s **acceptance window** (`character-voice-validation-rolling-state.json`) moves aside with it — the grades that let the retired record through its gate are the retired record’s, and the acceptance criterion averages the window, so keeping them would let a redone volume be refused by the grade of the file the reopen threw away (gotcha 113) — and a fresh record is opened carrying the reopen row so it knows it is a redo. A reason under 20 characters is refused. `--cascade=refuse` (default) names every later record built on this one and stops; `--cascade=retire` retires them with the same reason. The guard on the other side is what makes it safe: `openVolumeRecord` refuses a record whose source has been reopened since the copy was made, decided by comparing the reopen history **inside the copy** against the history the source holds now — not a timestamp, not a stamp (gotcha 114). No stage calls it; the only way onto it is typing the command. **A reopened volume that is not the first one arrives as an empty shell — only its reopen history, no `copy_provenance` row and none of the earlier volumes' claims — and the top-up door re-attaches the volume before it** (`copyForwardStore`'s `reattached` branch: no provenance row AND at least one `record_reopens` row for that volume, filed as a MEDIUM `reference-record-reattached-to-its-source`); without that branch the re-derived volume publishes only its own claims and nothing says so (gotcha 122). → `utils/reference-store/reopen.js`, `reopen-volume.js` |
| `npm run attribute-voice -- --volume=NN` | **Ask, once per doubted roster entry, who is speaking the words a claim quotes.** Two halves, and only one costs anything. The **deterministic half** (`utils/reference-store/attribution.js`) names every roster entry this volume filed claims under that this volume's own text does not measure as present — `--check` is that half alone, free, and it writes nothing. It deliberately does **not** name a speaker: the obvious rule (a cast name inside the cited quote is the speaker) was measured against both real records first and fires on 0 of volume 1's character claims and 10 of volume 2's, **all ten of them the addressee**, so the module decides only *when the record's own answer is in doubt*. The **reading half** (`character-voice/detective.js`) is the only part that asks the model anything, bounded four ways with no environment knob on any of them: one call per doubted entry (not per claim, chapter or character), `DETECTIVE_MAX_GROUPS` per run, `DETECTIVE_MAX_STEPS` **read-only** tool calls each — the write tools are not offered at all — and `DETECTIVE_TOKEN_BUDGET` prompt tokens after which the rest are reported as unanswered rather than paid for. An answer is filed in `attribution_answers` (schema **v7**), so the next run can tell "nobody asked" from "somebody asked and agreed": a second run over volume 02 costs **0 calls**. An answer that agrees closes the question. An answer that **disagrees** opens one `challenge_fact` row per claim, owned by the asking volume, each with its own quote checked against the book, and the claim the reference already published is **not edited and not moved** — it is marked `disputed` and stays where it is until somebody closes the dispute with `resolve_challenge`. **"narrator" is a real answer** and files its challenger with no roster entry at all (`key = null`, `extracted_as = "narrator"`), so the coverage rule — which counts rows in `cast` — is never asked to cover the narration, and a roster entry keyed by the word for the narration is refused at `upsertCast` and reported at HIGH if a record already holds one. An answer whose challenge cannot be filed leaves no answer row either. What the command does **not** do: it rewrites no artifact, seals nothing, files no `cast_alias` even when the answer is "the name is printed in a spelling this record cannot see" (an alias changes how every later volume measures that character — the owner's decision, not an inference from one scene; the notebook names the door instead of walking through it), and it does not widen how the record matches a name. **No stage calls it**, it is not in `index.js`'s step list, and the stage's cost and the offline call baseline are unchanged. Measured on the real volume 02: 1 group, 6 claims, **1 call, 8,208 prompt + 2,322 completion = 10,530 tokens**, 0 tool calls, answer `confirmed` → 蒲田, 0 challenges, both published files byte-identical; re-audited 3 findings / 0 HIGH and re-graded **80 / 80 / 79**, all "Pass with minor edits". → `utils/reference-store/attribution.js`, `utils/reference-store/narrator.js`, `character-voice/detective.js`, gotcha 121 |
| `npm run smoke` / `npm run calibrate` | Live checks (they call the real endpoint — not part of `npm test`) |
| `... --dry-run` / `--force` / `--volume NN` / `--chunked` | No AI calls (prompt dumps to `.dry-run/`) / regenerate anyway / one volume / force the chapter-by-chapter path |

Presence is measured per name and significance is judged per person: the pronoun's 951 matches stay under `俺`, the survivor's own row counts only his own name, and the coverage rule's chapter count is the union — which makes the guard stronger, and the report prints which names produced the number. `importVoice` now asks the same name question the extraction doors ask, because a document door that answers it separately puts a folded character's bullets back under the retired name and `renderVoice` does not render merged entries (gotcha 105). **The reading half is now a command of its own** (`extract-voice.js`, gotcha 106): a volume is read chapter by chapter into `character-voice-new.json` and then assembled by `rebuild-voice`, with no author agent and no feedback round. The published reference is the **accumulated** one (366 bullets: 196 established in volume 1, carried from its sealed record, plus 170 established in volume 2), the roster fold fired at the moment the record opened (`俺` → 如月雨露, 14 claims, one `cast_merges` row), the glossary completeness rule fired (34 imported / 86 carried / 4 refused), the audit found **0 HIGH and 3 MEDIUM**, and one real grading call scored it **80/100, "Pass with minor edits"** for 21,316 prompt tokens. What the route does **not** produce is `pov-map.md`, and the acceptance check names that file in its message list, so the stage's own grader cannot run on a rebuilt volume at all (gotcha 107) — **that gap is now closed from the artifact side**: `utils/reference-store/pov-map.js` renders the point-of-view claims the record already holds (adopted rows only, the same candidate filter `renderVoice` uses, plus the rows with no character to file them under, which a chapter-organised map has room for), it is **cumulative** — every earlier volume's sealed POV claims, in the order their own chapters appear — and `rebuild-voice --apply` writes it **before** it seals, so a refusal to overwrite an authored map stops the publish rather than leaving a sealed, ungradeable volume. Measured on the real volume 02: **61 claims over 11 chapter sections, 40 carried from volume 1 and 21 from volume 2, 37,334 bytes, 0 truncated bullets**, and re-graded through the stage's own `acceptanceCheck` with the map present: **82/100** against 80 without it and volume 01's 81 with its authored map. `--render-only` publishes that map for a **sealed** volume without touching a row (gotcha 109, which also records that the map's meaning changed from per-volume to cumulative and that the two routes now disagree about it). **Read-then-assemble became the voice stage's route, and then the only one** (`character-voice/assemble.js`): the stage opens the volume's record whatever the settings say, because on this route the record *is* the artifact's source. The gate is unchanged from the two-route era — deterministic audit, the same rubric, the same three files handed to the grader — and what the new route dropped is the **feedback pass**, because there is no author to ask: a failing grade quarantines both artifacts to `.rejected`, leaves the record a draft so the next volume's copy-forward refuses, and throws, so the step runner's ticket and post-mortem see it like any other failed step (one grade per volume, not five). The reading pass itself moved into `character-voice/reading.js` and is shared by the stage route and `extract-voice.js`, and it is where a **cut-off chapter** is caught: an extraction answer whose array never reached its closing bracket is half an answer, it is retried once at `EXTRACTION_RETRY_THINKING_LEVEL` (a constant, chosen by the volume-02 measurement — 6 and 1 claims at `xhigh`, 21 and 8 at `medium`), the better answer wins, both attempts are recorded in the chapter's partial, a chapter still cut off is named INCOMPLETE in `character-voice-reading.md` and appended to the validation report the grader reads, and `--chapter=<id>` re-reads one chapter by name (gotcha 111). The carry-forward guard had to learn the record's roster folds or it refuses a render that correctly dropped a folded heading — volume 02's real reference lost exactly `俺` and gained 7 characters (gotcha 110). **The redo slice is built and measured on volumes 1–2.** Reopening a published record is a recorded act (`reopen-volume.js`, `npm run reopen`): retire the file whole, never unseal a row, write the reason into `record_reopens`, move the volume’s acceptance window aside with the record it graded, and let the next run re-derive it — with `openVolumeRecord` refusing any record whose source has been reopened since the copy, decided from the reopen history the copy itself carries (gotcha 113, gotcha 114). A claim body carrying the writer’s own unfinished note is refused at filing and reported in the audit (`utils/reference-store/drafting.js`; 8,874 items measured, 12 flagged, 2 real defects, 0 false positives — gotcha 112). Rejected artifacts are **numbered** (`character-voice.md.rejected`, `.rejected.2`) through one shared door, and each volume folder gets a pipeline-written `.gitignore` whose whole content is `*.rejected*` — `series.db` and `series.db.retired-*` are deliberately **not** ignored, because they are the run’s memory. A chapter whose array closed cleanly and still lost a claim is now re-read for that claim (gotcha 116). **What the redo found is that the roster fold no longer fires**: its trigger was an authored heading (`俺（如月露露・第二章終盤）`) and the assembled route renders headings from keys, so volume 2 now holds 277 claims under `俺` and 2 under `如月露露`; the split is reported at MEDIUM rather than merged on a weaker signal, and closing it is an open decision, not an open bug (gotcha 115). **That split is now closed at the source, and the redo measured it.** A roster entry is never keyed by a bare first-person pronoun: `resolveExtractionName` files such a claim **unattached** — no cast row, the name the extraction wrote kept in `facts.extracted_as` (schema **v6**), and the audit prints it as `reference-claim-filed-without-a-roster-entry` at MEDIUM — and it *resolves* the pronoun whenever the record declares it, which it now does on its own: `importGlossary` reads the glossary's own Characters row ("Narrator: switches between 僕 and 俺") and declares 僕 and 俺 as aliases of 如月雨露 through `castAlias`, with the row as the reason. Measured against all 17 real glossaries before it was pinned: 17 hits, one per volume, all of them that same row, zero elsewhere; the glossary's 671 "Character Nicknames" rows were measured as the alternative and **rejected** (330 name one character, 73 name two, 268 name none, and the "one" cases are mostly joke aliases), because a declaration rule that guesses the owner files claims under the wrong person. Two entries declaring the same pronoun is reported as ambiguous, never settled by table order. `rebuildVoiceVolume` reads the same declarations out of the volume's `glossary.md`, so the door that bypasses the stage cannot disagree with the door that does not. Re-derived from the extraction output already on disk, **0 model calls for the reading**: volume 1 20 + 188 → 0 + 208, volume 2 282 + 190 → 0 + 472, totals 574 and 1360 unchanged, null-key claims unchanged, `cast_merges` still 0 in both — the claims moved from the pronoun to the person the glossary names, and neither published reference has a `### 俺` section any more (gotcha 117). **The extractor's scaffolding label no longer reaches published prose**: `drafting.js`'s third shape is a claim body opening with an all-caps label (`NEW CHARACTER. Uses あんた as …`), measured at **2,744 claim bodies / 9 hits / 1 distinct label / 0 false positives**, and it is **stripped rather than refused** — the claim is true and the record already says "new in this volume" as `established_volume`, so refusing it would be the guard doing damage; the candidate row keeps the raw text, and `screenClaim` runs *before* the already-filed comparison so a re-run recognises the claim it already filed (gotcha 118). **And the intake stopped reading its own notebook as the book**: `firstSourceInVolumeDir` now orders candidates — a real `.epub`, then the legacy staged name, then the first remaining text file *said out loud as a guess* — because a folder named `(01)` beside an archive named `(1).epub` missed the exact-name probe while Latin sorted before Japanese, and every stage was told volume 01 was 2,394 tokens and "single-segment" when it is 102,892 (gotcha 119). **And the author route is gone, not deprecated.** The character-voice stage has one route — read chapter by chapter, file, render, audit, grade, seal — `--route=` is refused for every value, and the stage makes **no agent call at all**: its whole cost is one extraction one-shot per chapter plus the grades. What the removed route was measured to have bought: on volume 01's live run it spent **166,370,184 tokens** across 25 agent turns and 11 one-shots, of which the four completed feedback agents were **53,656,318 tokens (32.3% of the run), 256 tool calls and 131 writes**; **exactly one acceptance grade was ever taken** (48/100, "Requires revision", blocking corrupted tail), there was **no re-grade after the feedback round**, and the file that route produced is quarantined on disk, not published. ## 3. The implementation folders

Every large module is a **thin barrel** that re-exports a folder of cohesive submodules.
`utils/translate.js` is 62 lines; `utils/translate/` is the code. This exists so an agent can
read one concern at a time instead of a 3,300-line file, and so a failure points at one file.

**The barrel is the public surface, and it is not negotiable.** Node resolves `translate.js`
before `translate/`, so every `require("./utils/translate")`, every test, and every
monkey-patch (`harness.runOneShot = …`) keeps working unchanged. When you split a module:

- keep every exported name available from the barrel, including the re-exported helpers;
- split along the seams the file already documents (its `// ─── Section ───` banners);
- never move a **guard table** out of its module's protected paths: `utils/tickets/`,
  `utils/resume/`, `utils/delivery-verify`, `utils/ledger`, `utils/runlock`, `utils/patches/`
  and `utils/reference-store/` are banned patch paths for the dev team, exactly like the single
  files they replaced (`utils/patches/rules.js`) — the ban covers the barrel and the folder alike,
  and only `utils/runlock.js` is still a single file today, so splitting one must not change what
  the ban covers;
- `__dirname` in a subfolder is the subfolder: a root-level task module needs a
  `projectRoot` alias passed down, a `utils/` module needs a `utilsDir` alias — and a
  **machine-state path built from it** moves folder with the file, so re-derive it and pin the

## 4. The rules that do not bend

1. **`harness.js` is the only way to talk to the model.** One-shot calls, agent handles, the
   gated file tools, the epub tools, the logging, the runaway/truncation guards, the idle
   deadline. Never bypass it to reach the provider. → `docs/architecture.md`
2. **The sandbox is the sandbox.** `createGatedFsTools` confines writes to the volume folder,
   refuses archives, and does not offer `deleteFile` at all. Do not weaken it, and do not
   advertise a tool the sandbox would refuse. → gotcha 8, gotcha 60
3. **A guard the role can switch off is not a guard.** The banned-option filter, the closed
   action menu, the banned patch paths, the pinned checks and `CONTEXT_MANAGED_ROLES` have no
   env knob on purpose. → gotcha 70, gotcha 75, gotcha 78
4. **Never let a stage persist empty output.** `runOneShot` throws on empty; agent stages are
   guarded by `assertWrote` / `assertRealOutput`. If you add a stage, add both guarantees. →
   gotcha 2, gotcha 58
5. **A cumulative artifact is amended in place, never reproduced.** The workflow copies the
   previous volume's file in, hands the agent a map of it, and a no-AI gate checks that nothing
   was lost. → gotcha 64, gotcha 65, gotcha 68
6. **Prompt files stay mode-agnostic**; mode-specific text is appended in code
   (`AGENT_TOOLS_NOTE`, `DIAGNOSIS_TOOLS_NOTE`, `DEVTEAM_TOOLS_NOTE`).
7. **JSDoc on every function**, using the named types from `types.js`. New code without JSDoc
   is a review blocker.
8. **Tests are plain `assert`, no framework**, and they point at a fixture — never at whatever
   `.env` says. A test that exercises the runner must not be able to touch the corpus it is
   protecting. → gotcha 69
9. **Update the docs after changes.** `docs/` is the current map; an agent reading it should be
   able to rely on it. If you add, remove or move something, update the map doc, the barrel
   table above if it is a split, and the gotcha list if you learned one.
10. **There are two repositories here, and you are inside the smaller one.** `ai-client/` is its
    own git repository (split out on 2026-10-06), so git paths here appear **without** an
    `ai-client/` prefix. The parent `oresuki/` is a *different* repository that ignores this folder
    and holds the account owner's in-progress translation output. Run git inside `ai-client/`, never
    reach upward — `git -C ..` is how somebody else's ~800 changes get committed — and keep scoping
    every call; never `git add -A`. → gotcha 75
11. **`npm test` is the gate**, and its last act is the offline pipeline loop plus the prompt
    audit. A green unit suite that breaks what the pipeline asks the model is still broken. →
    gotcha 62, gotcha 63

## 7. How work is dispatched here

The working shape in this repository is **one conductor and a series of single-use workers**.
The conductor (`.opencode/agents/conductor.md`, the `default_agent` in `.opencode/opencode.jsonc`)
does not implement: it scopes the slice, measures the starting state, hands the work to a
`builder` (`.opencode/agents/builder.md`), verifies the result against the disk, commits it,
and keeps the conversation free for deciding with the account owner. A `verifier`
(`.opencode/agents/verifier.md`) is read-only and checks a finished slice independently.
`/slice <task>` and `/verify <claim>` are the shortcuts. The procedure is in the
`dispatching-slices` skill (`.opencode/skills/dispatching-slices/SKILL.md`).

Three rules in it are load-bearing, and they are here because they were learned expensively:

1. **Every slice gets a brand-new worker session. Never resume one.** A worker session kept
   alive across several tasks — measured here: 473 messages, 3.3M input tokens, 54M cache-read
   tokens, 44 hours old — reported a finished slice with grades, token totals and a table of
   findings, and **none of it existed**: the modules were not on disk, the row counts were
   unchanged, and it invented a filename that appears nowhere in the tree and a book size of
   1,911 characters for a book that is 149,606. A worker deep in a compressed history answers
   by continuing its own story, and a continued story looks exactly like a report. The same
   job given to a session started fresh — 480 messages, 854k input tokens, six minutes —
   produced work that survived verification.
2. **A worker's report is a hypothesis until it has been checked against the filesystem.**
   `git status` for the files, `npm test` for the suite, a direct query for the rows, the
   `# Tokens:` headers in `<SERIES_LOCATION>/.run/logs/` for the cost, and the checksums taken
   before the dispatch for everything that was promised to survive. Nothing is committed on a
   report's word, and a claim that does not match the disk is reported to the account owner
   that plainly rather than patched over.
3. **One worker at a time — never two in flight, and never a worker alongside a run.** If two
   or more slices are needed, finish one (dispatch, verify, commit) before starting the next.
   This includes the tempting cases: two read-only investigators, or a builder plus a checker.

   **The reason is the inference server.** The model that powers OpenCode on this machine
   (`http://localhost:9200/v1`) answers **one request at a time**. Measured: two 400-token
   generations run in sequence took 3,134 ms and 2,224 ms; fired at the same instant they came
   back at 2,202 ms and 4,404 ms — the second took exactly twice as long, which is a queue, not
   parallelism. Running things concurrently buys nothing and lengthens every wait, which is what
   trips the harness's idle deadline and the stage timeouts. That one slot is shared by the
   worker sessions, a verifier running `npm test`, and the pipeline's own stage calls — so a
   worker is the one way to break the assumption from outside. `STAGE_CONCURRENCY` already
   defaults to 1 for this reason (docs/environment.md); **do not raise it, and do not write
   concurrent model calls into a stage, unless the endpoint genuinely serves parallel requests
   and that has been measured.**

   The second reason: every check that follows describes the repository at the instant it runs
   — `git status`, `npm test`, a database query, a checksum — so a worker writing while another
   one measures produces a reading of a state that never existed, and it gets reported as fact.

   The sequence is dispatch → wait → verify → commit → dispatch.
