# AGENTS.md — ai-client

**This file is the index.** The map, the architecture, the environment reference and the
hard-won gotchas live in `docs/`, one topic per file. Read the table in §2 before you open
anything, and read the gotchas that touch the area you are changing — they are the reason
most of this code looks the way it does.

## 1. What this is

An agentic AI client (v2.0.0, CommonJS, Node ≥ 22.19) that processes a light-novel series
**volume by volume** and produces translation-support artifacts — a glossary, a character
voice reference, a style guide, a wiki, a consistency audit — and then the translation
itself, chapter by chapter, through a multi-model chain (translate → verify → retranslate →
polish). It talks to any **OpenAI-compatible endpoint** through the Vercel AI SDK +
`@openharness/core`; tool-calling agents read the sources and write the outputs themselves
through sandboxed file tools.

On top of that sits a **delivery layer**: a deterministic step runner that assesses every
step, a run ledger that remembers what a run already tried, a ticket channel, a read-only
diagnostics role, a code-changing dev team, a delivery manager and a loop that drives them
(`index.js`, `delivery.js`, `diagnose.js`, `fix.js`, `autopilot.js`). See
`docs/delivery-layer.md`.

**Everything the pipeline writes — the deliverable and the run's own memory — lands in the
series folder**, not in this repo. The artifacts sit in the volume folders; the run's records
(its step reports, the ledger, the tickets, the patch records, the transcripts, the run lock)
sit in `<SERIES_LOCATION>/.run/`, which writes its own ignore rule so the records can be
committed with the books while the transcripts and the lock stay out. Change `SERIES_LOCATION`
and the next run gets its own memory instead of inheriting another series'. →
`configs/run-state.js`, `docs/environment.md`, gotcha 94.

### Quickstart

The books go in **`epub_source/`** (that folder *is* the default `SERIES_LOCATION` — unset
it and the pipeline looks there); the settings go in **`.env`** (`cp .env.example .env`).
`README.md` is the front door for someone who has never seen the project; this file is the
index for working on it.

| `npm run rebuild-voice -- --volume=NN` | **Rebuild one volume's character-voice reference from the extraction output it already produced** — no model call anywhere, and not part of a run. Rehearses on a copy under `--out` by default; `--apply --move-aside` is what replaces the volume's file, keeping the old one as `.rejected`, and it publishes `pov-map.md` **with** it, before the seal. **A rehearsal of a volume that has volumes before it renders only that volume's own claims** — the published file also carries every earlier volume's sealed record in (measured on volume 02: 12 sections rehearsed, 15 published) → gotcha 108. `--render-only` is the door that renders **only** `pov-map.md` from the record a volume already has: it files no row, seals nothing, and works on a sealed volume because publishing a map the record's own published claims describe edits no row (gotcha 109). → `docs/map-core.md`, gotcha 98 |
| `npm run reopen -- --volume=NN --reason="…"` | **Reopen one volume’s published reference record as a recorded act** — the door that exists because “this volume’s record is untrustworthy and every chapter must be re-read” used to have no legal answer. The act is **retire and re-derive, never unseal**: a row is written into `record_reopens` with the reason, `series.db` moves whole to `series.db.retired-<stamp>`, the volume’s **acceptance window** (`character-voice-validation-rolling-state.json`) moves aside with it — the grades that let the retired record through its gate are the retired record’s, and the acceptance criterion averages the window, so keeping them would let a redone volume be refused by the grade of the file the reopen threw away (gotcha 113) — and a fresh record is opened carrying the reopen row so it knows it is a redo. A reason under 20 characters is refused. `--cascade=refuse` (default) names every later record built on this one and stops; `--cascade=retire` retires them with the same reason. The guard on the other side is what makes it safe: `openVolumeRecord` refuses a record whose source has been reopened since the copy was made, decided by comparing the reopen history **inside the copy** against the history the source holds now — not a timestamp, not a stamp (gotcha 114). No stage calls it; the only way onto it is typing the command. **A reopened volume that is not the first one arrives as an empty shell — only its reopen history, no `copy_provenance` row and none of the earlier volumes' claims — and the top-up door re-attaches the volume before it** (`copyForwardStore`'s `reattached` branch: no provenance row AND at least one `record_reopens` row for that volume, filed as a MEDIUM `reference-record-reattached-to-its-source`); without that branch the re-derived volume publishes only its own claims and nothing says so (gotcha 122). **And a reopen retires a record, not the artifact rendered from it** (gotcha 148): `RETIRED_ACCEPTANCE_WINDOWS` (`utils/reference-store/reopen.js:383`) names only the character-voice window, so a reopened volume's `glossary-validation-rolling-state.json` survives, the glossary stage still counts that volume accepted, and it **skips the volume the reopen was meant to redo** — while `ensureVolumeGlossaryInRecord` reads the volume folder's `glossary.md` (`utils/reference-store/pipeline-store.js:166`) and imports it into a record holding no glossary rows, which re-imports exactly the rows the reopen just retired. Measured on 2026-10-14 while discarding volume 01: 273 facts / 18 cast / 10 chapters retired to `series.db.retired-20261014T024610`, with the 43,930-byte `glossary.md` and its `[93]` window still sitting in the folder. Whether the window list should name the glossary's too is open: adding it would force a paid glossary grade on a reopen asked for a voice record. → `utils/reference-store/reopen.js`, `reopen-volume.js` |
| `npm run attribute-voice -- --volume=NN` | **Ask, once per doubted roster entry, who is speaking the words a claim quotes.** Two halves, and only one costs anything. The **deterministic half** (`utils/reference-store/attribution.js`) names every roster entry this volume filed claims under that this volume's own text does not measure as present — `--check` is that half alone, free, and it writes nothing. It deliberately does **not** name a speaker: the obvious rule (a cast name inside the cited quote is the speaker) was measured against both real records first and fires on 0 of volume 1's character claims and 10 of volume 2's, **all ten of them the addressee**, so the module decides only *when the record's own answer is in doubt*. The **reading half** (`character-voice/detective.js`) is the only part that asks the model anything, bounded four ways with no environment knob on any of them: one call per doubted entry (not per claim, chapter or character), `DETECTIVE_MAX_GROUPS` per run, `DETECTIVE_MAX_STEPS` **read-only** tool calls each — the write tools are not offered at all — and `DETECTIVE_TOKEN_BUDGET` prompt tokens after which the rest are reported as unanswered rather than paid for. An answer is filed in `attribution_answers` (schema **v7**), so the next run can tell "nobody asked" from "somebody asked and agreed": a second run over volume 02 costs **0 calls**. An answer that agrees closes the question. An answer that **disagrees** opens one `challenge_fact` row per claim, owned by the asking volume, each with its own quote checked against the book, and the claim the reference already published is **not edited and not moved** — it is marked `disputed` and stays where it is until somebody closes the dispute with `resolve_challenge`. **"narrator" is a real answer** and files its challenger with no roster entry at all (`key = null`, `extracted_as = "narrator"`), so the coverage rule — which counts rows in `cast` — is never asked to cover the narration, and a roster entry keyed by the word for the narration is refused at `upsertCast` and reported at HIGH if a record already holds one. An answer whose challenge cannot be filed leaves no answer row either. What the command does **not** do: it rewrites no artifact, seals nothing, files no `cast_alias` even when the answer is "the name is printed in a spelling this record cannot see" (an alias changes how every later volume measures that character — the owner's decision, not an inference from one scene; the notebook names the door instead of walking through it), and it does not widen how the record matches a name. **No stage calls it**, it is not in `index.js`'s step list, and the stage's cost and the offline call baseline are unchanged. Measured on the real volume 02: 1 group, 6 claims, **1 call, 8,208 prompt + 2,322 completion = 10,530 tokens**, 0 tool calls, answer `confirmed` → 蒲田, 0 challenges, both published files byte-identical; re-audited 3 findings / 0 HIGH and re-graded **80 / 80 / 79**, all "Pass with minor edits". → `utils/reference-store/attribution.js`, `utils/reference-store/narrator.js`, `character-voice/detective.js`, gotcha 121 |
| `npm run release-translation -- --volume=NN --door=<step> --reason="…"` | **The only way past the freeze gate.** A published translation freezes what it was built from: `utils/prereqs/freeze.js` refuses to let `glossary`, `character-voice`, `style-guide`, `jump-in-wiki`, `consistency-audit`, `discover`, `extract` or the four manual reference doors rewrite the artifact a volume's `translation.md` was built on. The freeze is on **rewriting, not looking** — a verify-only pass, a rehearsal, a read-only check and filling a hole are not rewrites and stay allowed, while `--force`, a cascade, a changed source and a failed grade are rewrites and are refused per volume, naming the artifact, why the skip would have been cancelled, and the translations built on it. A reason under 20 characters is refused, the release is **per door**, it is standing rather than consumed, it **touches no translation file**, it is visible in the resume triage and the delivery report, and **no flag or setting reaches the gate**. No stage calls it. Known hole: the manager's `wipe-and-cascade` deletes a volume's outputs and the re-run that follows is excused as filling a hole — closing that changes the closed action menu and is the owner's decision. → `utils/prereqs/freeze.js` (a cover over `utils/prereqs/freeze/`), `release-translation.js`, `test/test-freeze-gate.js` (15 scenarios, 210 checks), gotcha 142 |

| `... --dry-run` / `--force` / `--volume NN` / `--chunked` | No AI calls (prompt dumps to `.dry-run/`) / regenerate anyway / one volume / force the chapter-by-chapter path |

## 3. The implementation folders

Every large module is a **thin barrel** that re-exports a folder of cohesive submodules.
`utils/translate.js` is 62 lines; `utils/translate/` is the code. This exists so an agent can
read one concern at a time instead of a 3,300-line file, and so a failure points at one file.

**The barrel is the public surface, and it is not negotiable.** Node resolves `translate.js`
before `translate/`, so every `require("./utils/translate")`, every test, and every
monkey-patch (`harness.runOneShot = …`) keeps working unchanged. When you split a module:

- keep every exported name available from the barrel, including the re-exported helpers;
- split along the seams the file already documents (its `// ─── Section ───` banners);
- never move a **guard table** out of its module's protected paths: `utils/tickets/`,
  `utils/resume/`, `utils/delivery-verify`, `utils/ledger`, `utils/runlock`, `utils/patches/`,
  `utils/reference-store/`, `utils/postmortem/` (added 2026-10-12, because the finding level table now lives
  there — gotcha 129) and `utils/prereqs.js` / `utils/prereqs/` (added 2026-10-13, because the step prerequisite table now lives
  there — gotcha 140 — and the freeze gate's door table now lives in `utils/prereqs/freeze/`) are banned patch paths for the dev team, exactly like the single
  files they replaced (`utils/patches/rules.js`) — the ban covers the barrel and the folder alike,
  and only `utils/runlock.js` is still a single file today, so splitting one must not change what
  the ban covers;
- `__dirname` in a subfolder is the subfolder: a root-level task module needs a
  `projectRoot` alias passed down, a `utils/` module needs a `utilsDir` alias — and a
  **machine-state path built from it** moves folder with the file, so re-derive it and pin the
  *default* in a test. → gotcha 80. Today the only machine-state path still built from a
  module's own location is `TOKEN_CALIBRATION_FILE` (deliberately repo-local — it measures this
  machine's endpoint); the run's records are resolved by `configs/run-state.js` from
  `SERIES_LOCATION` at **call** time instead, which is what gotcha 79's require-time trap would
  otherwise repeat. → gotcha 94

`utils/delivery-audit.js` is deliberately **not** split into a folder and is deliberately a **leaf**:
nothing under `utils/` requires it. `utils/tickets`, `utils/patches`, `utils/ledger` and `utils/runlock`
each resolve their own folder through `utils/postmortem`, so a module inside `utils/postmortem/` that
reached back for them would close a require cycle and hand them a half-built barrel. → gotcha 85

`test/module-layer.js` is the helper that lets a test which scans source text follow a module
into its folder (`readModuleLayer(rootDir, "utils/translate.js")`). The walk is **recursive
inside the named folder**, because a split layer nests: `glossary/` holds `glossary/extract/`,
`glossary/carry-forward/` and `glossary/settlement/`, and a scan that stopped one level down
would report a guarantee that lives in a nested submodule as a missing one — the same blindness
the helper exists to remove, one level further down (gotcha 161). It never leaves the named
folder, never follows a symlink, never walks `plan/` or a dotted folder, and stops at
`MAX_LAYER_DEPTH` (4), which `test/test-module-layer.js` pins against the deepest real layer
folder (1) so the bound cannot silently truncate a scan. `dropModuleLayer` forgets **the same
list**, so a "fresh process" simulation forgets a nested submodule's own state and not just the
face's. The default folder is still the one **named after the module**: `character-voice/task.js`
reads only itself, because its pin is about that entry point, and widening the default to "the
folder containing the file" would widen it for the wrong reason.

## 4. The rules that do not bend

1. **`harness.js` is the only way to talk to the model.** One-shot calls, agent handles, the
   gated file tools, the epub tools, the logging, the runaway/truncation guards, the idle
   deadline. Never bypass it to reach the provider. → `docs/architecture.md`
2. **The sandbox is the sandbox.** `createGatedFsTools` confines writes to the volume folder,
   refuses archives, and does not offer `deleteFile` at all. Do not weaken it, and do not
   advertise a tool the sandbox would refuse. → gotcha 8, gotcha 60
3. **A guard the role can switch off is not a guard.** The banned-option filter, the closed
   action menu, the banned patch paths, the pinned checks and `CONTEXT_MANAGED_ROLES` have no
   env knob on purpose. → gotcha 70, gotcha 75, gotcha 78
4. **Never let a stage persist empty output.** `runOneShot` throws on empty; agent stages are
   guarded by `assertWrote` / `assertRealOutput`. If you add a stage, add both guarantees. →
   gotcha 2, gotcha 58
5. **A cumulative artifact is amended in place, never reproduced.** The workflow copies the
   previous volume's file in, hands the agent a map of it, and a no-AI gate checks that nothing
   was lost. → gotcha 64, gotcha 65, gotcha 68
6. **Prompt files stay mode-agnostic**; mode-specific text is appended in code
   (`AGENT_TOOLS_NOTE`, `DIAGNOSIS_TOOLS_NOTE`, `DEVTEAM_TOOLS_NOTE`).
7. **JSDoc on every function**, using the named types from `types.js`. New code without JSDoc
   is a review blocker.
8. **Tests are plain `assert`, no framework**, and they point at a fixture — never at whatever
   `.env` says. A test that exercises the runner must not be able to touch the corpus it is
   protecting. → gotcha 69
9. **Update the docs after changes.** `docs/` is the current map; an agent reading it should be
   able to rely on it. If you add, remove or move something, update the map doc, the barrel
   table above if it is a split, and the gotcha list if you learned one.
10. **There are two repositories here, and you are inside the smaller one.** `ai-client/` is its
    own git repository (split out on 2026-10-06), so git paths here appear **without** an
    `ai-client/` prefix. The parent `oresuki/` is a *different* repository that ignores this folder
    and holds the account owner's in-progress translation output. Run git inside `ai-client/`, never
    reach upward — `git -C ..` is how somebody else's ~800 changes get committed — and keep scoping
    every call; never `git add -A`. → gotcha 75
11. **`npm test` is the gate**, and its last act is the offline pipeline loop plus the prompt
    audit. A green unit suite that breaks what the pipeline asks the model is still broken. →
    gotcha 62, gotcha 63

## 7. How work is dispatched here

The working shape in this repository is **one conductor and a series of single-use workers**.
The conductor (`.opencode/agents/conductor.md`, the `default_agent` in `.opencode/opencode.jsonc`)
does not implement: it scopes the slice, measures the starting state, hands the work to a
`builder` (`.opencode/agents/builder.md`), verifies the result against the disk, commits it,
and keeps the conversation free for deciding with the account owner. A `verifier`
(`.opencode/agents/verifier.md`) is read-only and checks a finished slice independently.
`/slice <task>` and `/verify <claim>` are the shortcuts. The procedure is in the
`dispatching-slices` skill (`.opencode/skills/dispatching-slices/SKILL.md`).

Three rules in it are load-bearing, and they are here because they were learned expensively:

1. **Every slice gets a brand-new worker session. Never resume one.** A worker session kept
   alive across several tasks — measured here: 473 messages, 3.3M input tokens, 54M cache-read
   tokens, 44 hours old — reported a finished slice with grades, token totals and a table of
   findings, and **none of it existed**: the modules were not on disk, the row counts were
   unchanged, and it invented a filename that appears nowhere in the tree and a book size of
   1,911 characters for a book that is 149,606. A worker deep in a compressed history answers
   by continuing its own story, and a continued story looks exactly like a report. The same
   job given to a session started fresh — 480 messages, 854k input tokens, six minutes —
   produced work that survived verification.

   **The one exception, and it is narrow.** A worker that stopped *before its report* because it
   reached a decision it was not allowed to make may be resumed **once**, with the answer written
   into the dispatch text, to finish that same slice — that session is shallow, holds one task, and
   needs an answer rather than a memory. Never to hand it new work, and the verification is
   unchanged. The guardrails are in the `dispatching-slices` skill.

   **Workers no longer have a question tool.** `builder` and `verifier` deny the `question`
   permission in their agent config, because a subagent that stops to ask the account owner blocks a
   child session nobody is watching, and two slices ended that way with the question still in the
   air. A worker that needs a decision writes it to `/tmp/opencode/<slice>-questions.md` — the
   options, what each costs, its recommendation — and then takes the branch that cannot damage
   anything or stops and puts the question at the top of its report.
2. **A worker's report is a hypothesis until it has been checked against the filesystem.**
   `git status` for the files, `npm test` for the suite, a direct query for the rows, the
   `# Tokens:` headers in `<SERIES_LOCATION>/.run/logs/` for the cost, and the checksums taken
   before the dispatch for everything that was promised to survive. Nothing is committed on a
   report's word, and a claim that does not match the disk is reported to the account owner
   that plainly rather than patched over.
3. **One worker at a time — never two in flight, and never a worker alongside a run.** If two
   or more slices are needed, finish one (dispatch, verify, commit) before starting the next.
   This includes the tempting cases: two read-only investigators, or a builder plus a checker.

   **The reason is the inference server.** The model that powers OpenCode on this machine
   (`http://localhost:9200/v1`) answers **one request at a time**. Measured: two 400-token
   generations run in sequence took 3,134 ms and 2,224 ms; fired at the same instant they came
   back at 2,202 ms and 4,404 ms — the second took exactly twice as long, which is a queue, not
   parallelism. Running things concurrently buys nothing and lengthens every wait, which is what
   trips the harness's idle deadline and the stage timeouts. That one slot is shared by the
   worker sessions, a verifier running `npm test`, and the pipeline's own stage calls — so a
   worker is the one way to break the assumption from outside. `STAGE_CONCURRENCY` already
   defaults to 1 for this reason (docs/environment.md); **do not raise it, and do not write
   concurrent model calls into a stage, unless the endpoint genuinely serves parallel requests
   and that has been measured.**

   The second reason: every check that follows describes the repository at the instant it runs
   — `git status`, `npm test`, a database query, a checksum — so a worker writing while another
   one measures produces a reading of a state that never existed, and it gets reported as fact.

   The sequence is dispatch → wait → verify → commit → dispatch.
